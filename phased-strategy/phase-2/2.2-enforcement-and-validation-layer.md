# Phase 2.2 — Enforcement And Validation Layer

## Goal

Attach the `workflow.yaml` contract to runtime behavior through bounded enforcement and layered validation.

Phase 2.2 does not try to prove perfect confinement. It makes each enforcement surface honest: the runtime must say whether it can deny an action, detect it after the fact, or record it for review.

2.1 defines the workflow source contract. 2.2 defines how `content-agent` constrains and validates behavior against that contract. 2.3 defines the durable run-record, trace, gate, and promoted-output evidence that records the result.

## Deliverables

- static checks for `workflow.yaml`, root YAML references, drift, and required fields
- context-admission checks against declared `context_dependencies`
- contract-aware checks for declared tools, capabilities, paths, inputs, outputs, gates, and budgets
- validation hooks defined or referenced by `workflow.yaml`
- a deny/detect/record posture for each enforcement surface
- run-mode-specific behavior for exploratory mode and governed continuous mode
- bounded source-linked drift checks for high-value stages
- hook boundaries that prevent false advancement without blocking unrelated human-directed work

## Enforcement Posture

Every enforcement surface must declare one of three first-implementation outcomes:

- `deny`: block the action before it can count as platform progress
- `detect`: allow the action to happen but surface a contract violation before completion or promotion
- `record`: preserve the event for review when denial or reliable detection is not yet practical

The first target is bounded denial and bounded checking, not total sandboxing. A workflow run is valid only when the relevant enforcement outcome is applied and recorded through the 2.3 evidence layer.

## Enforcement Surfaces

The first enforcement surfaces are:

- contract shape and references
- package and route resolution from package `status.yaml` and `pipeline_profiles.yaml`
- context admission from declared `context_dependencies`
- tool and capability use
- path reads and writes
- workflow preconditions
- workflow invariants
- workflow budgets
- expected outputs
- validation hooks
- review gates
- external mutation boundaries such as publish, distribute, upload, or archive sync
- lifecycle movement and promotion

Policy-sensitive actions such as external mutation, publication, distribution, lifecycle movement, gate approval, and promotion should be `deny` by default unless they occur through the governed path. Ordinary human-directed exploration should not be blocked by default, but it also should not count as valid platform progress until `content-agent validate` or a governed run validates it.

## Context Admission

Context admission is governed dependency management, not prompt stuffing.

The runtime should:

- load only declared context in governed runs, except where a surface is explicitly `detect` or `record`
- record loaded context paths and hashes through the 2.3 evidence layer
- surface undeclared context as a contract violation
- distinguish missing required context from extra undeclared context
- preserve enough information for resumption without turning Phase 2 into a repo-wide memory system

Context lifecycle governance remains outside 2.2 unless a concrete run exposes a failure. Decay, pruning, privacy, contradiction handling, and versioned reuse remain open pressure, not first-pass enforcement requirements.

## Validation Stack

Validation is lifecycle infrastructure, not a trailing test pass.

The first validation stack is:

1. static contract checks for `workflow.yaml`, root YAML surfaces, drift, and references
2. package and route resolution checks
3. context admission checks
4. allowed tool, capability, and path checks
5. precondition, invariant, budget, and recovery checks where supported
6. workflow validation hooks
7. bounded source-linked drift checks where they add real signal
8. trace and run-record completeness checks supplied by 2.3
9. review gate evidence and approval checks

Use the local `spec-diff` pattern as a design reference for bounded source-linked drift checks, not as a blanket repo-wide doctrine.

## Hooks And Run Modes

Hooks support enforcement, but they are not the primary mechanism for forcing arbitrary Codex session behavior.

In exploratory mode:

- hooks should warn, annotate, or record by default
- hooks should not block unrelated human-directed actions merely because they are outside an active workflow
- experimental workflow edits do not count as completed platform execution
- promotion, publication, lifecycle movement, and gate resolution still require explicit `content-agent` validation

In governed continuous mode:

- `content-agent` creates or loads a durable `resolved_run` when the run must survive response boundaries, gates, resume, or audit
- scriptable steps can execute directly through declared repo-native tools
- Codex-session-hosted steps must return control to `content-agent` for validation and continuation
- hooks may nudge or auto-resume safe validation-only checkpoints when expected outputs exist
- hooks should block false advancement, publish, approval, or lifecycle mutation outside the governed path
- review gates and external mutation gates always stop for explicit approval

Hooks fail at the boundary they guard. A pre-action hook can deny an attempted publish, lifecycle mutation, gate approval, or write outside an allowed path. A post-action hook can detect or record drift, undeclared context, missing outputs, stale gates, or trace incompleteness. If a hook cannot reliably deny or detect a surface, the architecture should mark that surface as `record` and avoid stronger claims.

## Content-Agent Validation Responsibilities

`content-agent validate` should be able to run without advancing lifecycle state.

At minimum it should check:

- the workflow contract is loadable and schema-valid enough for the target command
- workflow README and `workflow.yaml` references are not materially drifting
- root policy, gate, and profile references resolve
- package `status.yaml` supplies the lifecycle state needed for routing
- declared context dependencies can be located and hashed
- required tools, capabilities, paths, outputs, gates, and validation hooks are declared
- each enforcement surface has an explicit deny/detect/record posture
- gate and trace requirements are present where the workflow declares gated or promotable outputs

`content-agent run` and `content-agent resume` should apply the same checks as part of governed execution. `content-agent status` and `content-agent next` should surface blocking violations without mutating source authority.

## Acceptance Read

2.2 is done when:

1. each platform-targeted workflow can declare validation hooks, context checks, path/tool checks, gates, budgets, and expected outputs consistently
2. each enforcement surface declares `deny`, `detect`, or `record`
3. undeclared tools, capabilities, paths, and context are either denied or surfaced as contract violations according to their declared posture
4. policy-sensitive actions are denied outside the governed path
5. exploratory mode warns or records without blocking unrelated human-directed work
6. governed continuous mode validates between scriptable/model-mediated steps and stops cleanly at review or external mutation gates
7. at least one high-value stage family has bounded source-linked drift checking
8. `content-agent validate` can report contract, context, path/tool, gate, and trace-readiness findings without promotion

## Non-Goals

- no claim of perfect conformance
- no total sandbox for all human actions
- no global validator framework for every package
- no full semantic provenance layer
- no context lifecycle governance beyond admission checks
- no autonomous hook-driven session runner that replaces `content-agent`
- no dashboard-led validation UX
- no standalone security program
