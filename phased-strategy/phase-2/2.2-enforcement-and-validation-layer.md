# Phase 2.2 — Enforcement And Validation Layer

## Goal

Attach the workflow contract to runtime behavior.

The platform should be able to deny undeclared tools, undeclared paths, and undeclared context where practical, and it should be able to emit bounded validation or drift findings where denial is not yet possible.

## Deliverables

- contract-aware checks for undeclared tools and undeclared paths
- context-admission checks against `required_context`
- per-stage validation hooks defined in `workflow.yaml`
- a bounded source-linked drift-check pattern for high-value stages

## Enforcement Targets

The first enforcement targets should be:

- stage execution against `allowed_tools`
- stage execution against `allowed_paths`
- visible detection of undeclared context outside `required_context`
- policy-sensitive boundaries such as publish, distribute, and external mutation

Do not target perfect runtime confinement in this phase.

## Validation Targets

Validation should be treated as lifecycle infrastructure, not a trailing test pass.

The first validation layer should cover:

- workflow contract sanity
- expected output presence
- stage-specific validation hooks
- bounded source-linked drift checks where they add real signal

Use the local `spec-diff` pattern as a design reference, not as a blanket repo-wide doctrine.

## Acceptance Read

2.2 is done when:

1. undeclared tools and undeclared paths are either denied or surfaced as contract violations
2. undeclared context is visible in execution records
3. platform-targeted workflows can declare and run validation hooks consistently
4. at least one high-value stage family has bounded source-linked drift checking

## Non-Goals

- no claim of perfect conformance
- no global validator framework for every package
- no full semantic provenance layer
- no dashboard-led validation UX
