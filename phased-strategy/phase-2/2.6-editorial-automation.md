# Phase 2.6 — Editorial Automation

## Goal

Add bounded editorial automation after governed runs, gate decisions, and article-polish boundaries are stable.

The automation should produce structured reports, violations, and source-improvement suggestions. It should not rewrite, promote, publish, or move lifecycle state on its own.

## Starting Point

2.6 assumes:

- 2.4 runtime commands can run, gate, review, and resume from file-backed evidence
- 2.5 cockpit can expose gates and run evidence without becoming authority
- `article_polish` has a stable `workflow.yaml` contract
- `voice_consistency_guide.md` remains the voice authority for publication writing
- package content artifacts remain package-local

## Scope

Start with report-producing automation for:

- voice and style checks
- banned phrase and tone violations
- claim/evidence trace cautions
- reference, link, image, and artifact placement checks
- release-readiness support checks
- repeated correction patterns that suggest source improvements

Reports should be structured enough to be machine-readable and human-reviewable.

Likely output locations:

- package-local `artifacts/` or review folders when the report concerns package content
- `reviewable-runs/logs/` when the report is run evidence
- `reviewable-runs/gates/` when the report creates or supports a review stop

## Runtime Rules

- Automation runs under workflow contracts.
- Reports must identify source files and relevant checks.
- Violations are advisory or gate-supporting until a workflow contract makes them blocking.
- Any rewrite remains a human or Codex-session action, not an automatic mutation.
- Publication, external mutation, promotion, and lifecycle movement still require gates.

## Initial Checks

Candidate first-pass checks:

- voice-guide ban list detection
- paragraph rhythm and auditor-tone checks
- unsupported superlative or authority claims
- stale or missing references
- broken local links
- image/slide/transcript placement mismatch for article-polish packages
- release-readiness checklist completeness

Each check should declare:

- id
- input paths
- output report path
- severity vocabulary
- blocking policy, if any
- workflow hook that invokes it

## Acceptance Read

2.6 is done when:

1. `article_polish` can produce a structured editorial report under the governed runtime path.
2. reports distinguish errors, warnings, and advisory suggestions.
3. reports link every finding to source files or artifacts.
4. repeated issues can be summarized as source-improvement suggestions.
5. no report autonomously rewrites content, approves gates, promotes outputs, publishes, or mutates lifecycle state.
6. release-sensitive findings can support a review gate without replacing the gate decision.

## Non-Goals

- no autonomous article rewrite
- no automatic publication
- no lifecycle movement
- no replacing `voice_consistency_guide.md`
- no general analytics product
- no semantic provenance graph
- no claim that style automation can decide publication quality alone
