# Phase 2.4 — Gate Runtime And `content-agent`

## Goal

Implement the deterministic `content-agent` runtime over the file-backed contracts and evidence established in 2.1, 2.2, and 2.3.

The runtime should make package state, next actions, run evidence, and review gates operable from files without becoming an LLM persona, dashboard-first control plane, or second workflow language.

## Starting Point

Phase 2.4 assumes these surfaces already exist:

- per-workflow `workflow.yaml` contracts
- root `harness_policy.yaml`, `pipeline_profiles.yaml`, and `gate_contracts.yaml`
- package `status.yaml` manifests
- `content-agent validate`
- YAML evidence validation for `resolved_run`, `run_record`, and `review_gate`
- retained Phase 2.3 examples under `reviewable-runs/`

2.4 should consume those surfaces. It should not redesign workflow contracts, promoted-output state, or package taxonomy.

## Command Surface

The v1 command vocabulary remains:

- `content-agent init`
- `content-agent status`
- `content-agent next`
- `content-agent run`
- `content-agent resume`
- `content-agent review`
- `content-agent validate`

Implementation may land in smaller slices, but the final command names should not be replaced by older `stage:*` or `workflow:*` names.

## Implementation Slices

### 2.4a Read-Only Runtime

Implement first:

- `content-agent status`
- `content-agent next`
- `content-agent review list`
- `content-agent review inspect`

These commands should read file-backed truth and print stable text or JSON. They should not approve gates, write run records, publish, promote, or mutate lifecycle state.

Minimum behavior:

- load package status when `--package` is supplied
- load workflow contracts and root YAML surfaces
- list pending and resolved gate artifacts
- show recent YAML run records and legacy lightweight JSON logs separately
- report validation health using the existing `validate` machinery
- treat pending gates as blockers for governed next actions

### 2.4b Gate Decision Runtime

Implement after read-only review is stable:

- `content-agent review approve`
- `content-agent review reject`
- `content-agent review defer`

Gate decisions should:

- update the YAML gate artifact with a structured decision record
- preserve separate approval dimensions for quality, external mutation, lifecycle movement, and promotion
- write follow-up run-record evidence
- avoid lifecycle movement unless the gate explicitly approves that dimension and the route allows it
- keep deferral non-mutating

External mutation approval must remain visibly distinct from content quality approval.

### 2.4c Resolved Run Creation

Implement durable `resolved_run` creation for governed, gated, resumable, continuous, or audit-relevant runs.

Minimum behavior:

- resolve package, workflow, route/profile, context dependencies, allowed tools, allowed paths, selected steps, selected gates, budgets, recovery semantics, and output targets
- persist the resolved run only when the policy says it is required
- validate the resolved run immediately after writing it
- leave exploratory previews transient unless a gate, resume, or audit boundary requires persistence

### 2.4d Scriptable Run And Gate Stop

Implement bounded scriptable execution before Codex-session-hosted or model-mediated steps.

Minimum behavior:

- run declared scriptable steps only when command, tool, path, context, budget, and output checks pass
- write a run record for each governed or proof-relevant run
- stop at declared review, external-mutation, lifecycle, or promotion gates
- create a YAML review gate artifact when a gate is reached
- return cleanly with the gate id and file path

### 2.4e Resume

Implement `content-agent resume` only after gate decision semantics are stable.

Minimum behavior:

- resume from an approved gate or durable `resolved_run`
- reject resume when validation fails, approval dimensions are insufficient, or the gate is still pending
- write follow-up run-record evidence
- preserve the original run and gate artifacts as inspectable history

## Runtime Rules

- Files remain authoritative.
- `content-agent` executes declared contracts; it does not invent workflow semantics.
- All writes must stay inside policy-allowed paths.
- All governed writes must be source-linked through run evidence.
- Pending gates block governed progress.
- Approval is explicit, dimensional, and durable.
- External mutation is denied unless an external-mutation gate explicitly approves it.
- Lifecycle movement and promotion are denied unless the gate and route explicitly allow them.

## Validation

Every implementation slice should keep these checks green:

```bash
./content-agent validate
npm run check:workflow-model
npm run check:reviewable-runs
npm run check
```

New commands should support `--format json` where their output becomes a downstream input.

## Acceptance Read

2.4 is done when:

1. `content-agent status` reports package state, pending gates, recent runs, and validation health from files.
2. `content-agent next` resolves the next eligible action while respecting pending gates and package routes.
3. `content-agent review` can list, inspect, approve, reject, and defer YAML gates.
4. `content-agent run` can create validated resolved runs, execute safe declared scriptable steps, write run records, and stop at file-backed gates.
5. `content-agent resume` can continue only from approved gates or valid durable resolved runs.
6. gate decisions write follow-up run evidence and preserve distinct approval dimensions.
7. no command treats logs, gates, or resolved runs as source authority over workflow contracts, root policy, or package state.
8. retained proof runs use real package paths, not synthetic package classes.

## Non-Goals

- no local cockpit in 2.4
- no autonomous rewrite, promotion, publication, or distribution authority
- no model-provider adapter requirement
- no separate LLM persona
- no hidden database of runtime state
- no event-sourced replay requirement
- no standalone promoted-output manifest
