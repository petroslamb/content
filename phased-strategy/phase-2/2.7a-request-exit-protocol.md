# Phase 2.7a - Request Exit Protocol Implementation

## Goal

Generated subagent requests include enough exit protocol, skill recommendations, and verification requirements that workers can finish cleanly without hooks.

## Summary

Phase 2.7a is the implementation subphase after Phase 2.7. It hardens the request/result protocol that already exists around `codex_session` handoffs. The target is better generated instructions, stricter result evidence, and regression proof that malformed or incomplete worker exits cannot look complete.

This subphase implements request/result protocol hardening, not hooks and not a broad multi-agent scheduler.

The implementation should keep the existing runtime boundary:

- `content-agent` may emit deterministic request artifacts.
- `content-agent` may defer before model-mediated work.
- `content-agent` may validate returned result and integration-decision artifacts.
- `content-agent` must not spawn models, perform LLM work, clear gates from generic results, or mutate external systems.

## Starting Point

Phase 2.7 strategy is done. It defines parent/subagent discipline, a required worker exit protocol, future request/result additions, a skill plan, and a design-only hook posture.

The current `content-agent` runtime already emits both generic and explicit subagent requests:

- generic `codex_session` handoffs are synthesized from workflow id, step id, consumes, produces, output targets, admitted inputs, and source hashes.
- explicit `agent_contract` handoffs are preserved for `essay_iteration.run_cold_replacement_review`.
- `same_session` compatibility still defers at a `codex_session` boundary without emitting a request.
- existing result validation checks schema version, request id, package/workflow/run identity, verdict enum, source-hash echoes, and line-grounded findings.

Hooks remain design-only. This document does not activate hooks.

## Implementation Slices

### 1. Generated Request Fields

Every new generated subagent request emitted under the 2.7a protocol should include:

```yaml
handoff_protocol_version: phase-2.7a
recommended_skills:
  - name: content-agent-handoff
    path: workflows/skills/content-agent-handoff/SKILL.md
    reason: Read the repo-local handoff closeout protocol before producing a result.
    source: phase-2.7a
    priority: first
exit_protocol:
  required: true
  steps:
    - read_request_and_declared_inputs_only
    - write_declared_workflow_outputs
    - write_declared_result_artifact
    - self_check_result_metadata_schema_hashes_verdict_and_findings
    - run_declared_verification_commands
    - repair_result_artifact_if_shape_validation_fails
    - return_minimal_final_response
  negative_verdicts_still_require_valid_result: true
  integration_decision_allowed_by_worker: false
  final_response_fields:
    - result path
    - workflow output path if any
    - validation command
    - success boolean
    - minimal blockers
verification_requirements:
  required: true
  commands:
    - id: content_agent_validate
      command: ./content-agent validate --workflow <workflow_id> --package <package> --format json
      required: true
      success_exit_codes:
        - 0
  result_schema_checks:
    - kind
    - schema_version
    - request_id
    - package
    - workflow
    - run
    - verdict
    - source_hashes
    - findings
    - verification.commands
  source_hash_checks:
    require_result_hash_echo: true
    stale_on_mismatch: true
  artifact_checks:
    declared_result_path_required: true
    declared_output_targets_required: true
operator_prompt_fragment: |
  Read the request artifact and declared inputs only. Write the declared outputs
  and result artifact. Run the declared verification commands. Final response
  must include only result path, workflow output path if any, validation command,
  success boolean, and blockers.
```

`recommended_skills` are advisory operator aids, not authority. The request artifact, workflow YAML, package status, root policy, gate contracts, and integration decisions remain authoritative.

The `content-agent-handoff` skill should be recommended first for all 2.7a requests once it exists. Workflow-specific skills may be added when the request already admits their files or the workflow contract clearly names the capability. Examples: `alphaxiv` for alphaXiv retrieval work, `markitdown-paper-intake` for paper intake, and `youtube-data-api` for authenticated YouTube inspection. The implementation must not infer broad new read/write authority from a skill recommendation.

`operator_prompt_fragment` is appropriate only as a derived convenience. If implemented, it must be generated from the request fields and must not become a separate prompt language with extra obligations. If the runtime prints or writes a prompt fragment for the parent operator, it should quote the same result path, output targets, exit protocol, and verification commands already present in the request.

### 2. Result Artifact Validation

For any result tied to a 2.7a request, validation should require frontmatter metadata that includes:

```yaml
verification:
  commands:
    - command: ./content-agent validate --workflow <workflow_id> --package <package> --format json
      exit_code: 0
      success: true
      short_failure_summary: none
```

`verification.commands[]` shape:

- `command`: non-empty string.
- `exit_code`: integer when the process ran; `null` only when the command could not be launched and the result verdict is not `pass`.
- `success`: boolean.
- `short_failure_summary`: non-empty string; use `none` only when `success: true`.

Validation should continue to enforce the existing checks:

- result `kind: subagent_result`.
- `schema_version` matches the current content-agent schema.
- `request_id` matches a generated request.
- package, workflow, step, and run fields match the request.
- `verdict` belongs to the request's allowed verdict enum.
- result source hashes repeat request source hashes.
- stale hash mismatches are blocking.
- findings are line-grounded with `path` or `file` plus a positive line number.
- integration decisions use allowed decisions and reference known result ids.

The new missing-verification check should be gated by the matching request, not by historical artifact location. Existing request/result artifacts that predate 2.7a should remain legacy-compatible. The simplest implementation boundary is:

- new generated requests set `handoff_protocol_version: phase-2.7a`.
- results for those requests must include valid `verification.commands[]`.
- older generated requests without `handoff_protocol_version` are validated by the current schema/hash/verdict rules and do not fail solely because they lack `verification.commands[]`.

This avoids retroactively breaking retained proof artifacts while making every new request exit enforceable without hooks.

### 3. `content-agent-handoff` Skill

The first new skill in the later implementation should live at:

- `workflows/skills/content-agent-handoff/SKILL.md`

It should explain how a worker reads a request artifact, restricts itself to declared inputs, writes the requested output and result artifacts, records verification commands, handles stale or malformed cases, and returns the minimal final response.

The implementation should also list the skill in `workflows/skills/README.md`.

This strategy document does not create that skill.

### 4. Tests And Regression Proofs

The implementation should add focused tests around the existing request/result runtime rather than broad orchestration tests.

Required proof cases:

- Generic request emission: a non-gate generic `codex_session` emits a request with `handoff_protocol_version`, `recommended_skills`, `exit_protocol`, `verification_requirements`, expected artifact paths, source hashes, and no model-spawn behavior.
- `same_session` compatibility: `same_session` still defers without a request, and no 2.7a request-field validation is applied when no request exists.
- Cold-review gate blocking: `replacement_north_star` remains blocked unless the cold-review result is current, `verdict: pass`, and the integration decision accepts the pass.
- Stale hash: a result whose source hashes do not match the request remains blocked.
- Malformed result: missing or invalid frontmatter, unknown verdicts, request mismatch, or ungrounded findings fail validation.
- Missing verification: a result for a 2.7a request that lacks `verification.commands[]` fails validation.

Useful concrete test expansion:

- Extend existing generic handoff tests to assert the new request fields.
- Extend existing same-session tests to assert no request artifact is written.
- Extend existing stale-hash and malformed-result tests to keep their current blocking behavior.
- Add one minimal generated 2.7a request/result fixture where all existing fields are valid but `verification` is missing; validation must fail on that specific gap.
- Add one passing 2.7a result fixture with a successful `./content-agent validate ... --format json` command entry.

## Boundaries And Non-Goals

- no hook activation
- no model spawning by `content-agent`
- no broad multi-agent scheduler
- no parent-loop automation hidden inside `content-agent`
- no gate clearing from generic results
- no integration decision written by a worker unless the request explicitly assigns that role
- no external mutation
- no lifecycle movement
- no workflow YAML rewrite
- no runtime permission inferred from `recommended_skills`
- no retroactive rewrite requirement for historical request/result artifacts

## Acceptance Read

Phase 2.7a implementation is done when:

- generated 2.7a requests contain `recommended_skills`, `exit_protocol`, and `verification_requirements`.
- generic requests still defer and never spawn models.
- `same_session` compatibility still defers without writing a request.
- result validation requires `verification.commands[]` for 2.7a requests.
- existing schema, request-id, package/workflow/run, verdict, source-hash, stale-hash, line-grounding, and integration-decision validation still work.
- `content-agent-handoff` exists under `workflows/skills/content-agent-handoff/SKILL.md` and is listed in `workflows/skills/README.md`.
- hooks remain inactive and design-only.
- generic results cannot clear review gates.
- cold replacement review remains gate-critical and explicit.
- tests cover generic request emission, same-session compatibility, cold-review gate blocking, stale hashes, malformed results, and missing verification.
- validation passes with retained legacy artifacts still present.
