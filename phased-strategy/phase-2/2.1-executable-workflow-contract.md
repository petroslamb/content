# Phase 2.1 — Executable Workflow Contract

## Goal

Make per-workflow `workflow.yaml` files the highest functional truth layer for workflow behavior.

The runtime should no longer depend on README prose, scattered frontmatter, or skill text to infer what a workflow may do. README files remain the human explanation surface. Skills remain capability and operator-guidance surfaces. `workflow.yaml` owns the machine contract that `content-agent` can load, validate, resolve, and execute.

Phase 2.1 defines the source contract. Phase 2.2 defines enforcement and validation behavior. Phase 2.3 defines trace, run-record, gate, and promoted-output minimums.

## Deliverables

- one authored `workflow.yaml` beside each platform-targeted workflow README
- a practical v1 vocabulary for identity, versioning, stability, kind, grouping, context, capabilities, paths, steps, outputs, validation, gates, traces, and the behavioral envelope
- drift checks between workflow README metadata and `workflow.yaml`
- a declared migration boundary from current workflow README/frontmatter conventions to the new machine contract
- thin hand-authored discovery wrappers for the first workflows, where useful for Codex routing
- a documented relationship between `workflow.yaml`, root YAML surfaces, package `status.yaml`, and derivative compatibility artifacts

## First Workflow Set

Start with workflows that define the essay lifecycle and external publication path:

- `paper-intake`
- `alphaxiv-research`
- `essay-iteration`
- `article-polish`
- `substack-publishing`
- `substack-archive-sync`

Do not start by converting every workflow in the repo. Additional workflows should enter 2.1 only when a real package-path run needs them.

## Contract Decisions

- `workflow.yaml` is authored directly and checked for drift.
- `workflow.yaml` is YAML-first. JSON is allowed only for rebuildable caches, API responses, or external tool interoperability.
- The adjacent README remains the human explanation surface and operator orientation.
- The YAML owns machine authority for execution planning.
- README prose and skill guidance must not carry runtime permission, path, gate, routing, or completion semantics alone.
- Root `harness_policy.yaml`, `gate_contracts.yaml`, and `pipeline_profiles.yaml` constrain workflow contracts but do not replace per-workflow `workflow.yaml`.
- Package `status.yaml` supplies package lifecycle state; `workflow.yaml` supplies workflow behavior.
- The retired `harness_contract.yaml` compatibility index is not authored workflow authority.
- `content-agent` consumes workflow contracts through the v1 command surface: `init`, `status`, `next`, `run`, `resume`, `review`, and `validate`.
- A workflow may bind skills as capabilities, but skills do not decide lifecycle routing, gates, package state, or promotion.
- Experimental workflows may exist, but they enter execution only through explicit operator request, package route/status decision, or pipeline profile.

## V1 Workflow Contract Vocabulary

Each `workflow.yaml` should define enough source authority for `content-agent` to resolve and validate a run without README parsing.

### Identity And Scope

- `workflow_id`
- `version`
- `stability`: `canonical` or `experimental`
- `workflow_kind`: `stage`, `module`, or `overlay`
- `workflow_group`
- `summary`
- `package_classes`
- package and path inputs
- outputs

### Context And Capabilities

- `context_dependencies`
- tool and capability requirements
- `allowed_paths`
- related skills, if the workflow binds operator guidance or helper capabilities

Context dependencies are governed dependencies, not prompt stuffing. The contract should declare what must be loaded, why it is needed, and how the runtime can record the loaded path and hash. Context lifecycle rules such as decay, pruning, privacy, contradiction handling, and versioned reuse stay outside 2.1 unless a real run exposes a concrete failure.

### Behavioral Envelope

Each workflow should carry a small behavioral envelope:

- `preconditions`: facts that must hold before the workflow starts
- `invariants`: facts that must remain true while the workflow runs
- `budgets`: bounded limits such as time, files, steps, retries, or external operations
- `recovery`: declared behavior for retry, resume, rollback, defer, or fail-closed cases

The envelope is not a proof system. Add only fields that can produce checkable runtime signal on real workflows.

### Execution Steps

Each workflow should define ordered steps. Each step should define:

- `id`
- `title` or short label
- `mode`: scriptable, Codex-session-hosted, review-gated, or external-mutation-gated
- command, named executor, or declared manual/model-mediated action
- consumed inputs
- outputs
- validation hooks or checks
- gate reference when the step is gated
- trace/run-record requirements when the step creates or promotes evidence

Scriptable steps should run through declared repo-native tools where possible. Codex-session-hosted steps should return control to `content-agent` for validation and continuation.

### Validation, Gates, And Trace References

The workflow contract should name validation and gate requirements without absorbing all 2.2 or 2.3 details.

It should define or reference:

- static contract checks
- context admission checks
- allowed path and tool checks
- workflow validation hooks
- review gates
- trace and run-record requirements

Gate classes should resolve through `gate_contracts.yaml`. Route-level sequencing should resolve through `pipeline_profiles.yaml`. Run records, resolved runs, review gate artifacts, and promoted-output state are derivative execution evidence, not additional authored workflow contracts.

## Discovery Wrappers

Phase 2.1 should support workflow discovery without turning skills into workflow authority.

For the first workflow set, create thin hand-authored discovery wrappers only where they materially help Codex find and select a workflow. A wrapper should:

- use a concise skill-style description for when to enter the workflow
- point to the canonical `workflow.yaml` and workflow README
- name related execution skills
- avoid repeating process rules that belong in the workflow contract

Do not generate discovery wrappers in v1. Keep the discovery surface flat across workflows and skills. Preserve hierarchy through `workflow_group`, `workflow_kind`, and `stability`; add group-level wrappers only after the flat surface becomes noisy in real use.

## Migration Plan

1. Inventory the first workflow set and record existing README/frontmatter fields that currently imply machine behavior.
2. Author one `workflow.yaml` beside each target workflow README.
3. Move machine-readable behavior into YAML while leaving explanatory prose in the README.
4. Add drift checks for identity, summary, version, stability, and README/YAML references.
5. Add thin discovery wrappers only for workflows where Codex discovery is otherwise weak.
6. Keep compatibility indexes out of the active authority path; validate primary Phase 2 surfaces directly.
7. Update `workflow-yaml-schema.md` after this spec is stable so the schema reflects 2.1 rather than competing with it.

## Acceptance Read

2.1 is done when:

1. the target workflow set has authored `workflow.yaml` files
2. the practical v1 vocabulary is stable across that set
3. the machine contract is sufficient to plan execution without README parsing
4. context dependencies, capabilities, paths, steps, outputs, validation hooks, gates, and trace requirements are declared in YAML
5. preconditions, invariants, budgets, and recovery semantics exist where they produce checkable signal
6. drift checks exist and pass for the converted workflows
7. discovery wrappers, if present, point back to `workflow.yaml` and do not duplicate process authority
8. `content-agent next`, `run`, and `validate` can consume the contract vocabulary in design or implementation tests

## Non-Goals

- no full enforcement layer in 2.1; enforcement semantics belong in 2.2
- no full trace/provenance layer in 2.1; run-record and promoted-output minimums belong in 2.3
- no gate runtime implementation in 2.1, beyond declaring gate references
- no dashboard/cockpit work
- no full conversion of every workflow in the repo
- no generated discovery-wrapper system in v1
- no standalone promoted-output manifest
- no default subagent-hosted execution model
