# Phase 2.7 - Agent Handoff Discipline

## Goal

The parent session orchestrates; subagents do model-mediated work; deterministic artifacts prove what happened.

## Summary

Phase 2.7 formalizes the post-2.6 handoff architecture without changing runtime code in this subphase.

The local platform already has deterministic workflow contracts, validation, review gates, run evidence, `content-agent`, cockpit, and bounded editorial reporting. The remaining gap is operator discipline around model-mediated `codex_session` work: every `codex_session` boundary can become a clean-context subagent handoff, but the deterministic runtime must stay deterministic and the worker must leave enough evidence for the parent session to inspect and integrate the result.

This subphase makes that boundary explicit:

- `content-agent` remains infrastructure, not an LLM actor.
- the visible parent or orchestrator creates fresh subagents with `fork_context=false`.
- subagents perform the model-mediated work against admitted files and request artifacts.
- request, result, validation, gate, and integration artifacts prove what happened.
- workflow-specific operator guidance moves into skills, while workflow YAML and request artifacts remain authoritative.
- hooks remain a later enforcement layer, designed but not active by default.

## Starting Point

2.7 assumes:

- 2.4 can run, defer, gate, review, resume, and validate against file-backed evidence.
- 2.5 can inspect runtime evidence without becoming authority.
- 2.6 can produce bounded editorial reports without autonomous promotion.
- `harness_policy.yaml` owns the global `codex_session_handoff` posture.
- `reviewable-runs/README.md` documents subagent request, result, and integration-decision stores.
- generated `codex_session` requests already prove the core runtime boundary: emit a request, defer, and do not spawn a model.

## Runtime Boundary

`content-agent` may:

- resolve workflow, package, run, and step state from source authority.
- emit deterministic subagent request artifacts.
- defer at `codex_session` boundaries.
- validate returned result and integration-decision artifacts.
- check gates and record evidence.
- preserve `same_session` compatibility by deferring without a request when that mode is selected.

`content-agent` must not:

- spawn models.
- perform LLM work.
- continue model-mediated workflow steps after emitting a request.
- silently integrate a subagent result.
- clear gates without the declared gate and integration requirements.
- invent workflow-specific rules not declared by `workflow.yaml`, root policy, gate contracts, package state, or the handoff request.

The parent or orchestrator may:

- spawn or create a fresh worker subagent with `fork_context=false`.
- provide the request artifact and minimal task instructions.
- wait for the expected result artifact.
- inspect, validate, and make any required integration decision.
- send targeted corrections to the same worker when the result is malformed or incomplete.

The parent or orchestrator must not hide the handoff behind an unrecorded runtime loop. Until a separate orchestration phase is explicitly defined, the parent session remains the visible organizer.

## Required Subagent Exit Protocol

Every worker subagent receiving a Phase 2.7 handoff must complete this exit protocol before returning control:

1. Write the expected result artifact at the path declared by the request.
2. Self-check the result frontmatter, schema fields, request id, source hashes, verdict vocabulary, findings shape, and any workflow-specific required sections.
3. Run `./content-agent validate` with the workflow, package, and runtime inputs derived from the request artifact.
4. Repair its own artifacts when validation fails because of result shape, stale hashes, missing verification, invalid verdicts, or malformed frontmatter.
5. Return a final response containing only:
   - result path
   - workflow output path, if any
   - validation command
   - success boolean
   - minimal blockers

This protocol applies even when the worker's substantive answer is "defer", "fail", or "stale". A negative result still needs a valid artifact and an honest verification record.

## Request Artifact Additions

Later runtime work should extend generated request artifacts with these advisory and enforcement fields:

- `recommended_skills`: skill names that the worker should read before executing the handoff.
- `exit_protocol`: the required worker closeout steps for the specific request.
- `verification_requirements`: deterministic commands, schema checks, artifact checks, source-hash checks, and workflow-specific validation expectations.

These fields should be generated from workflow contracts, root policy, and request context. They should not make skills authoritative over `workflow.yaml`, package `status.yaml`, root policy, gate contracts, or the request artifact itself.

## Result Artifact Additions

Later validation work should require generated subagent results to include:

- `verification.commands[]`

Each command entry should record:

- `command`
- `exit_code`
- `success`
- `short_failure_summary`

The result artifact should not contain an integration decision unless the request explicitly assigns that role to the worker. By default, integration remains a parent-run responsibility recorded under `reviewable-runs/integration-decisions/`.

## Skill Plan

Skills are operator manuals and execution aids. They are not the authority layer.

The first new skill should be:

- `content-agent-handoff`: how to read a request artifact, run the required exit protocol, write a compliant result, and avoid unauthorized integration decisions.

The next workflow skills should be:

- `essay-iteration`: packet discipline, cold replacement review behavior, source-hash echoing, line-grounded findings, and replacement gate blockers.
- `topic-discovery`: clean-context topic discovery handoffs, candidate-paper inspection, and essay-object ranking.
- `release-gate`: release-surface inspection, external mutation boundaries, and gate-supporting verification.

The skill layer may explain how to work. The authoritative surfaces remain:

- workflow `workflow.yaml`
- package `status.yaml`
- root policy, gate, and profile YAML files
- generated subagent request artifacts
- review gates and integration decisions

## Hook Plan

Hooks are design-only for Phase 2.7. Do not enable them by default in this subphase.

A future Stop hook may enforce the same exit protocol by checking the active handoff artifact before a worker session ends. The hook should:

- no-op unless active handoff artifacts make it relevant.
- identify the expected result path from the request.
- verify required result frontmatter and schema fields.
- verify `verification.commands[]` is present when the request requires it.
- suggest or run only deterministic validation commands that the request declares.
- block or warn on malformed worker artifacts according to future hook policy.

Hooks may guard protocol, but they must not:

- advance workflows.
- spawn models.
- clear gates.
- write integration decisions unless the request explicitly assigns that role.
- mutate package lifecycle state.
- publish or perform external mutation.

## Subagent Supervision Procedure

The approved supervision model for this subphase is:

1. Parent creates or provides a single implementation handoff to a fresh worker subagent with `fork_context=false`.
2. Worker write paths are exactly the paths named in the handoff.
3. Worker must not edit runtime code, workflow YAML, hooks, or skills unless those paths are explicitly owned by the handoff.
4. Worker runs deterministic docs and validation commands that are available, including `git diff --check`.
5. Worker writes the expected result artifact with changed files, validation commands, success boolean, and blockers.
6. Parent waits for the result artifact.
7. Parent inspects the changed docs and result artifact.
8. Parent runs validation.
9. Parent sends targeted correction requests to the same worker if needed.
10. Parent finalizes only after checks pass or a real blocker is explicit.

The parent supervises. The worker implements. The deterministic artifacts provide the review surface.

## Test Plan

Strategy-doc validation:

- links from `phase-2/README.md` and `milestones.md` to this file resolve.
- wording preserves Phase 2 authority boundaries and does not claim autonomous publication.
- the runtime boundary says `content-agent` emits, defers, validates, checks gates, and records evidence; it does not spawn models or do LLM work.
- the hook posture remains design-only.
- the skill posture says skills are operator manuals, not authority.

Runtime regression expectations to preserve:

- generic `codex_session` handoff emits a request and defers.
- `same_session` still defers without request.
- explicit cold replacement review contract still blocks `replacement_north_star` unless result is `pass` and integration is `accept_pass`.
- lost-plot proof run remains blocked.

Future implementation tests:

- generated requests include `exit_protocol`.
- subagent result with missing verification fails validation.
- stale hashes still block.
- malformed result frontmatter still fails validation.
- recommended skills are present but advisory, not authority.

## Acceptance Read

2.7 is complete as a strategy subphase when:

1. the Phase 2 roadmap lists 2.7 after 2.6.
2. the handoff runtime boundary is documented without turning `content-agent` into a model runner.
3. the subagent exit protocol is explicit enough for a fresh worker to follow.
4. request and result artifact additions are specified for later implementation.
5. skill and hook plans are clear, with hooks design-only and disabled by default.
6. the supervision procedure distinguishes parent orchestration from worker implementation.
7. validation expectations include both current regression checks and future implementation tests.

## Assumptions

- Phase location is Phase 2.7, not Phase 3.0.
- Hook posture is design-only in this subphase; request-level exit protocol is the active enforcement mechanism for now.
- Implementation is delegated to a subagent; the parent session supervises only.
- The next gate-critical explicit contract after cold replacement review remains a later decision, with `release_gate.inspect_release_surfaces` as the leading candidate.
- No hidden orchestrator is introduced in Phase 2.7; the parent session remains the visible organizer until an external orchestration phase is explicitly defined.

## Non-Goals

- no runtime code changes in this subphase
- no workflow YAML changes
- no hook activation by default
- no new skill implementation in this subphase
- no autonomous publication
- no lifecycle movement
- no external mutation
- no hidden multi-agent scheduler
- no replacement for review gates or integration decisions
