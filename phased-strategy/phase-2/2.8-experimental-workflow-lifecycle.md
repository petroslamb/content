# Phase 2.8 - Experimental Workflow Lifecycle

## Goal

Make experimental workflows first-class without letting them blur source authority.

Phase 2.8 formalizes how experimental workflows are created, handled, run,
proven, promoted into canonical workflow status, or retired. It is a
strategy-only policy layer. It does not add `content-agent` commands, change the
`workflow.yaml` schema, change validators, or add new runtime behavior.
Operationalization work may still migrate workflow docs and `workflow.yaml`
contracts under this policy; that is tracked workflow work, not a Phase 2.8
runtime expansion.

Phase 2.8a operationalizes this policy in
[`2.8a-experimental-workflow-operating-process.md`](2.8a-experimental-workflow-operating-process.md).
That implementation adds fixed README lifecycle fields and a standalone
experimental-workflow checker; it does not change `content-agent` commands,
`workflow.yaml` schema fields, or promotion semantics.

The core rule is:

> Experiments may run explicitly and produce evidence, but they must not silently
> replace canonical lifecycle paths until they pass the promotion bar.

## Lifecycle States

Use this state vocabulary when discussing experimental workflows:

| State | Meaning | Required Surface |
| :--- | :--- | :--- |
| `proposed` | The idea exists, but the workflow has no stable operating surface yet. | Note, issue, strategy packet, or package-local finding. |
| `documented` | A workflow README explains the human process and expected outputs. | `workflows/<workflow>/README.md`. |
| `contracted` | The workflow can be loaded and validated as a governed experimental workflow. | `workflow.yaml` with `stability: experimental`. |
| `active_experiment` | The workflow is being run explicitly against real packages. | `./content-agent validate` and `./content-agent run` evidence. |
| `proof_backed` | At least one clean governed real-package run exists. | Retained Reviewable Runs evidence. |
| `promotion_candidate` | The workflow has met the proof bar and is ready for human approval. | Two clean proofs in distinct contexts plus a promotion note. |
| `canonicalized` | The workflow is now a main/canonical workflow. | `stability: canonical` plus any route, gate, and docs updates. |
| `retired` | The experiment is closed, superseded, or no longer active. | README closeout note or archive note. |

## Creation Rules

Every experimental workflow starts as a workflow README. The README should state:

- the workflow id, kind, group, and `stability: experimental`
- the problem the experiment tests
- the package classes it may operate on
- the expected outputs
- the approval boundaries
- the conditions under which the experiment should stop

Any experimental workflow intended for governed execution must add a
`workflow.yaml` contract before it can count as a governed experiment. That
contract should use existing Phase 2 fields only:

- `stability: experimental`
- explicit context dependencies
- allowed read and write paths
- declared tools and skills
- validation hooks where available
- gate references for movement, promotion, external mutation, or quality review
- trace requirements for source-linked run records

Do not add new schema fields for 2.8. If the current schema cannot express a
needed behavior, record that as a limitation in the workflow README or strategy
notes rather than silently encoding a private convention.

## Handling Rules

Experimental workflows can be run on demand, but they must not silently replace
canonical lifecycle paths.

An experimental workflow must not:

- enter a default route without explicit profile or route changes
- move package lifecycle state on its own
- publish or mutate external systems without the existing approval gates
- promote drafts, artifacts, claims, or package state without a promotion gate
- replace a canonical workflow merely because one run succeeded
- become the only explanation of a shared process while remaining README-only

Experimental profiles may exist in `pipeline_profiles.yaml` when they make route
boundaries explicit. An experimental profile is not a default route merely
because it is listed there. It should stay opt-in until the workflow is
canonicalized and the default route change is explicitly approved.

## Run Rules

Governed experimental runs use the same operator surface as canonical runs:

```bash
./content-agent validate --workflow <workflow_id> --package <package>
./content-agent run --workflow <workflow_id> --package <package>
```

For model-mediated steps, use the Phase 2.7a handoff protocol when applicable:

- request artifacts under `reviewable-runs/subagent-requests/`
- result artifacts under `reviewable-runs/subagent-results/`
- `handoff_protocol_version: phase-2.7a`
- declared verification requirements
- result validation with `verification.commands[]`

Direct scripts, manual experiments, and README-only guided runs may inform the
design, but they do not count as governed proof for promotion.

## Proof Rules

Only real-package governed runs count as promotion proof.

Promotion evidence must include:

- a real package path, not a synthetic demo
- a `workflow.yaml` contract active for the run
- `./content-agent validate` success before or during the run
- a retained run record under `reviewable-runs/logs/`
- durable resolved state when the run is gated, resumable, continuous, or
  audit-relevant
- gate artifacts when the workflow stops for review, lifecycle movement,
  promotion, or external mutation
- explicit blockers if the run cannot finish cleanly

README-only experiments and direct-script runs may be cited as design evidence,
but they cannot satisfy the promotion bar.

## Promotion Rules

An experimental workflow becomes a canonical/main workflow only after all of
these are true:

1. It has two clean governed real-package proofs in distinct contexts.
2. The proofs use `./content-agent validate` and `./content-agent run`.
3. Any model-mediated steps follow the Phase 2.7a handoff protocol when
   applicable.
4. The workflow has no unresolved approval-boundary ambiguity.
5. A human approval or strategy/review artifact explicitly accepts promotion.
6. The workflow README and `workflow.yaml` agree on the promoted behavior.
7. Route/profile updates are made only if the workflow belongs in a default or
   midstream path.
8. Gate contract updates are made only if the workflow introduces a new movement
   decision.
9. Retained proof links are recorded in the relevant strategy, README, or review
   artifact.
10. `stability` changes from `experimental` to `canonical`.

Promotion is not automatic. A workflow can be useful, repeatable, and still stay
experimental if it is narrow, risky, auth-heavy, or not part of the main
lifecycle.

## Retirement Rules

Experiments should not remain ambiguous active surfaces after they fail, go
stale, or get superseded.

Retire an experimental workflow when:

- the tested workflow shape did not produce useful outputs
- the workflow was replaced by a canonical workflow or another experiment
- required external services or auth surfaces are no longer viable
- repeated runs expose unresolved authority or safety problems
- no package has a plausible use for the workflow anymore

Retirement should leave a short closeout note in the workflow README or an
archive note. The note should say what was tested, why it stopped, what evidence
exists, and whether any pieces should be preserved as skills, scripts, or
canonical workflow updates.

## Boundaries

Phase 2.8 does not implement:

- new `content-agent` commands
- new `workflow.yaml` fields
- runtime-validator or schema changes
- cockpit changes
- automatic migration of experiments into default routes or canonical status
- autonomous promotion, publication, lifecycle movement, or external mutation
- hidden scheduling or model spawning by `content-agent`

Those remain out of scope unless a later implementation phase promotes them into
the appropriate authority surfaces.

The Phase 2.8a checker is a separate operating-process guard over existing
contracts and README state. It does not expand the runtime.

## Done When

Phase 2.8 is done when:

1. this policy exists as a tracked strategy packet
2. Phase 2 index docs link to it
3. `architecture.md` points the existing experimental-workflow rule here
4. docs and workflow checks pass
5. future experimental workflow work can identify its lifecycle state, proof
   requirement, promotion bar, or retirement path without inventing new policy
6. Phase 2.8a documents the operating process and
   `npm run check:experimental-workflows` verifies the README/YAML/evidence
   guardrails for experimental workflows
