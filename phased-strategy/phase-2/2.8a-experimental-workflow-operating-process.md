# Phase 2.8a - Experimental Workflow Operating Process

## Goal

Turn the Phase 2.8 lifecycle policy into a repeatable operating process for
experimental workflows without changing the runtime contract.

Phase 2.8a is an implementation discipline over existing surfaces:

- workflow READMEs
- adjacent `workflow.yaml` contracts when a workflow is governed
- retained Reviewable Runs evidence
- `./content-agent validate`
- `scripts/check_experimental_workflows.py`

It does not add `content-agent` commands, change the `workflow.yaml` schema,
promote workflows automatically, or make any experimental workflow a canonical
or default route.

## Five Moves

### 1. Intake

Create or update the workflow README first.

The README frontmatter must declare:

- `workflow_id`
- `workflow_kind`
- `stability: experimental`
- `workflow_group`
- `required_context`
- `expected_outputs`
- `done_when`
- `approval_gate`

The body must include `## Phase 2.8 Lifecycle State` with these fixed fields:

- `State`
- `Governed contract`
- `Proof runs`
- `Promotion status`
- `Promotion blockers`

README-only future experiments are allowed only at `State: documented`. They
are human playbooks, not governed workflows, until an adjacent `workflow.yaml`
exists.

### 2. Contract

If the experiment should be invokable through `content-agent`, add an adjacent
`workflow.yaml` using existing Phase 2 fields only.

Governed experimental contracts must keep:

- `stability: experimental`
- non-empty `outputs`
- non-empty `steps`
- `validation.static_checks`
- `validation.context_checks`
- `trace.run_record: required`
- `trace.resolved_run`

The checker verifies that the README and YAML agree on workflow identity and
that `./content-agent validate --workflow <workflow_id> --format json`
succeeds. Contracting a workflow makes it explicitly runnable; it does not make
it canonical, default-routed, or promotion-eligible.

### 3. Run/Prove

Run governed experiments explicitly:

```bash
./content-agent validate --workflow <workflow_id> --package <package>
./content-agent run --workflow <workflow_id> --package <package>
```

Promotion proof requires retained real-package evidence. A clean proof cannot
have terminal status `deferred` or failed validation. Deferred runs may show
that the contract loads and produces useful artifacts, but they do not satisfy
the promotion bar.

### 4. Promote

Promotion remains manual and proof-gated.

An experimental workflow may claim `promotion_candidate` only when its lifecycle
block records:

- at least two clean real-package proof run ids
- explicit approval text accepting promotion consideration
- no unresolved approval-boundary ambiguity

The final promotion still requires a scoped edit that changes the relevant
authority surfaces intentionally. No checker, run record, or successful run may
canonicalize a workflow by itself.

### 5. Retire

Retire an experiment when it is obsolete, failed, superseded, unsafe, or no
longer useful enough to keep active.

The README should keep a short closeout in the lifecycle block or a nearby
retirement note. Retirement preserves the evidence trail; it does not delete
proof runs or silently migrate pieces into canonical workflows.

## Checker

Run:

```bash
npm run check:experimental-workflows
```

The checker inspects every `workflows/*/README.md` with
`stability: experimental`. It allows README-only future experiments only at
`State: documented`; the current seven experimental workflows must remain
governed experimental contracts.

The checker enforces the operating fields above, verifies governed contract
shape, runs the read-only `content-agent validate` command for governed
experiments, and blocks premature `promotion_candidate` claims.

## Boundaries

Phase 2.8a must not:

- add or change `content-agent` commands
- add or change `workflow.yaml` schema fields
- change package lifecycle state
- edit canonical/default routing to favor an experiment
- promote an experiment automatically
- treat README-only experiments as governed
- treat deferred or failed runs as clean promotion proof
- mutate external publication, YouTube, Substack, or package artifacts as part
  of checking

The checker is an operating-process guard. It is not a runtime expansion.
