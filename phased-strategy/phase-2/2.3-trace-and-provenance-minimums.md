# Phase 2.3 — Trace And Provenance Minimums

## Goal

Add the minimum execution-evidence structure needed for source-linked debugging, governed resume, review gates, and trust-sensitive promotion decisions.

Traces, run records, resolved runs, and gates are derivative execution evidence. They do not become the source of truth and they do not redefine `workflow.yaml`, package `status.yaml`, root policy/profile/gate YAMLs, or package content artifacts.

2.1 defines the workflow source contract. 2.2 defines enforcement and validation posture. 2.3 defines what must be written down when `content-agent` resolves, validates, runs, stops, resumes, or promotes work.

## Deliverables

- YAML-first execution evidence under `reviewable-runs/`
- durable `resolved_run` files when a run is governed, gated, resumable, continuous, or audit-relevant
- source-linked run records that include context paths and hashes
- workflow id, version, and hash in run records
- parent artifact ids or paths where a step consumes prior outputs
- validation results and deny/detect/record outcomes recorded in run evidence
- gate ids recorded when a review or external-mutation stop is reached
- YAML-backed review gate artifacts that can stop and resume execution
- a stable small vocabulary for promoted-output state:
  - `authority_order`
  - `claim_state`
  - `contradiction_state`
  - `validation_state`
  - `trace_state`

## Execution Evidence Placement

`reviewable-runs/` holds generated execution evidence:

- `reviewable-runs/resolved-runs/` for persisted resolved runs
- `reviewable-runs/logs/` for source-linked run records
- `reviewable-runs/gates/` for pending and resolved review gates

Package directories continue to hold package lifecycle state, drafts, source files, previews, and content artifacts. Execution evidence should point back to those files rather than moving them into `reviewable-runs/`.

Execution evidence is maintained by `content-agent`. Humans inspect it and decide through the CLI or cockpit rather than hand-authoring run records, resolved runs, or gate files.

YAML is the default persisted structured format. Markdown with YAML frontmatter is acceptable for human-readable run summaries only when the structured fields remain machine-readable.

## Object Boundaries

### Resolved Run

`resolved_run` is the runtime view of one workflow contract applied to one package and run request.

Persist a durable `resolved_run` when:

- the run is governed continuous mode
- the run must survive response boundaries
- a review or external-mutation gate may stop execution
- resume is expected
- audit or proof-run retention is needed

Exploratory previews may remain transient. A `resolved_run` is not a new workflow language and should not be hand-authored.

Minimum fields:

- run id
- package target
- workflow id, version, and contract hash
- run mode
- resolved package route or pipeline profile
- admitted context list
- allowed tools, capabilities, and paths after policy resolution
- selected steps and gates
- budgets and recovery semantics after resolution
- output targets

### Run Record

`run_record` is the source-linked account of what happened.

Every governed or proof-relevant run should record:

- run id and optional resolved-run id/path
- package target and package state reference
- workflow id, version, and contract hash
- run mode
- start and end timestamps
- invoking command or entrypoint
- context file paths and content hashes
- consumed input artifacts and parent artifact ids or paths
- produced output artifacts and paths
- validation hooks/checks run
- validation results
- deny/detect/record outcomes for enforcement surfaces
- gate ids reached or resolved
- approval decisions, if any
- external mutation attempts and approval references, if any
- terminal status: completed, gated, failed, deferred, rejected, or superseded

Run records are audit and debugging evidence, not source authority.

### Review Gate

`review_gate` is a durable stop/resume object.

A gate artifact should record:

- gate id
- gate type from `gate_contracts.yaml`
- run id and resolved-run reference
- package target
- workflow id and step id
- reason execution stopped
- required reviewer decision
- required evidence paths
- external mutation flag, when applicable
- allowed decisions: approve, reject, defer
- resume target or recovery behavior
- decision record when resolved

External mutation approval is distinct from content quality approval. A gate may require both, but the artifact should not collapse them into one ambiguous approval.

### Promoted-Output State

Phase 2 starts with a small promoted-output state model, not a standalone provenance graph.

Use this vocabulary:

- `authority_order`
- `claim_state`
- `contradiction_state`
- `validation_state`
- `trace_state`

V1 records promoted-output state inside run records and review gate artifacts. Do not add a separate promoted-output manifest until repeated promoted outputs need independent lifecycle tracking across multiple runs or gates.

## Trace Minimum

Every governed or proof-relevant run should be able to record:

- which workflow contract governed execution
- which package state and route were resolved
- which context files were loaded and their hashes
- what inputs or parent artifacts were consumed
- what outputs were produced
- what validators ran and what they returned
- which enforcement surfaces denied, detected, or recorded violations
- what gate stopped the run, if any
- what approval decision resumed, redirected, or closed the run

That is the minimum useful source-linked debugging surface.

## Provenance Minimum

Phase 2 provenance is bounded provenance for promotion decisions.

This state model should be usable for:

- promoted claims
- publish approvals
- major draft promotions
- any other output that crosses an irreversible or trust-sensitive boundary

It should answer four practical questions:

- what source contract and package state produced this output?
- what context and parent artifacts influenced it?
- what validation and review evidence exists?
- what contradiction, approval, or trace caution remains?

It should not attempt host-independent verification, full semantic provenance graphs, agent registries, or automated contradiction resolution.

## Acceptance Read

2.3 is done when:

1. governed, gated, resumable, or proof-relevant runs persist enough `resolved_run` state to resume from files
2. run records consistently include the trace minimum fields
3. gate-linked runs preserve the gate id and resume/recovery behavior
4. review gate artifacts distinguish quality approval from external mutation approval
5. promoted-output state is recorded in run records and gates using the stable vocabulary
6. deny/detect/record outcomes from 2.2 are visible in run evidence
7. traces can support source-linked debugging without being misdescribed as source authority
8. no standalone promoted-output manifest is introduced without a concrete repeated-output lifecycle need

## Non-Goals

- no full semantic provenance graphs
- no automatic contradiction resolution
- no claim that logs are the authority surface
- no analytics product layer
- no event-sourced replay requirement for the minimum trace layer
- no host-independent verifiable trace format
- no agent registry
- no standalone promoted-output manifest in v1
