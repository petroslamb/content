Abstract
We propose using natural language outlines as a novel modality
and interaction surface for providing AI assistance to developers
throughout the software development process. An NL outline for
a code function comprises multiple statements written in concise
prose, which partition the code and summarize its main ideas in the
style of literate programming. Crucially, we find that modern LLMs
can generate accurate and high-quality NL outlines in practice.
Moreover, NL outlines enable a bidirectional sync between code
and NL, where a developer can change either code or NL and have
the LLM automatically update the other. We discuss many use cases
for NL outlines: they can accelerate understanding and navigation
of code and diffs, simplify code maintenance, augment code search,
steer code generation, and more. We then propose and compare
multiple LLM prompting techniques for generating outlines and
ask professional developers to judge outline quality. Finally, we
present two case studies applying NL outlines toward code review
and malware detection.

organization and accessibility. A table of contents presents organi-

notes may also be interleaved with the content as chapter or sec-
tion headings. Modern examples of outlines include the “Contents”
sidebar on Wikipedia pages listing the section headings, and for
programming, the “Outline view” in VS Code and the “Symbols
pane” on GitHub list the classes and functions in a code file. These
outlines also assist navigation by jumping to the corresponding

Summarization is another way to accelerate understanding of
a document. Scientific papers have an abstract, and business doc-
uments may have an executive summary, to help readers quickly
understand the key points without reading the entire text. Even if
one does read the entire text, reading the summary beforehand may
still improve understanding [6, 40]. Recent works apply machine
learning and LLMs toward automatic text summarization [ 35] and
code summarization [ 7–9 , 22, 34 , 66 , 68 ], with many summary styles
for different purposes and audiences [17 , 30 , 47 , 60 ]. For example,
upon straightforwardly asking Gemini or ChatGPT to summarize
a piece of code, one usually receives long paragraphs explaining
each aspect of the code in detail, often totaling more text than the
code itself. Such explanations are useful for learning but are not
optimized for helping an experienced developer work more quickly.
Instead, we desire a concise summary that efficiently conveys the
key ideas, with clear alignment between the summary and the code.
Another common way to improve the clarity of code is to incorpo-
rate natural language (NL). Writing docstrings, comments, helpful
error messages, and descriptive identifier names are well-known as-
pects of good coding style [ 5]. In computational notebooks or other
forms of literate programming [38 ], code and explanatory NL are in-
terleaved in a file that is both executable and self-documenting. NL
is generally easier for humans to read than code, so well-written NL
can help developers understand the associated code more quickly.
Using these themes of outlining, summarization, and literate pro-
gramming, we propose using LLMs to generate a new form of code
explanation: natural language outlines (NL outlines). An NL outline
consists of natural language statements that partition the code into
logical sections, while summarizing each section of code with con-
cise wording. The outline may be shown interleaved with the code
or displayed separately, depending on the application. NL outlines
are a particularly appealing modality for AI developer assistance
due to their broad applicability: in addition to helping developers
understand and navigate code, Fig. 1 illustrates our vision of how
NL outlines can be used throughout the software development, e.g.,
for code generation and maintenance, code search, and code review.

are a conceptual foundation and framework enabling many possible

2 Natural Language Outlines
A natural language outline (NL outline) for a function or snippet of
code consists of one or more statements written in concise prose,
which are aligned with the code and partition it into semantically-
coherent sections, such that each outline statement summarizes the
section of code it aligns to.
As an example, Fig. 2a shows a Python function from an author’s
prior project. Even though the code is self-contained and only
uses common libraries, it still takes a considerable amount of time
for a developer to parse the code and decipher the steps taken to
achieve its goals. A docstring might help somewhat, but docstrings
usually discuss the function’s contract instead of its implementation
strategy which may be more pertinent when editing the code.
To gain a high-level understanding of the implementation, one
may instead read the NL outline in Fig. 2b which mirrors the code’s
ideas and structure, while being more concise (using about half
as many characters) and easier to read (English versus code). The
compact nature of the outline would also reduce scrolling when
browsing through the file. If one wishes to see more details or
reference the code “source of truth,” the outline may also be dis-
played as comments or annotations interleaved with the code in
the style of literate programming [38 ], as shown in Fig. 2c. In this
format, the outline provides visual structure and allows the reader
to seamlessly switch between reading NL or code syntax as needed.
Some developers already write these kinds of comments manually,
even despite the risks that they might become stale and are time-
consuming to maintain (but Section 3 offers solutions for both),
adding to the familiarity of NL outlines as a concept.
But with recent advancements in large language models (LLMs),
there is little need for developers to write NL outlines manually,
as modern LLMs can generate high-quality NL outlines even for
proprietary code outside their training data (Section 5). Thus, we
propose that NL outlines can be used as a means to provide AI
assistance to developers, with many use cases illustrated in Fig. 1
and further discussed in Section 3. NL outlines are designed to im-
prove developer efficiency for code authors, maintainers, and users.
NL outlines serve a very different purpose than existing auto-
matic code summarization techniques (see Section 8). Compared
to generating a docstring which describes a function’s contract
for API users [ 31], an NL outline instead summarizes a function’s
implementation for developers maintaining or extending it. Even
though NL outlines can be displayed alongside the code like inline
comments (Fig. 2c), they differ in content and design. Typical inline
comments contain sparse notes about design rationales, subtle pit-
falls, and remaining tasks [ 52 , 54 ], but Scalabrino et al . [58] found
that such comments are not correlated with perceived or actual
understanding of code. In contrast, NL outlines focus on boosting
high-level understanding of the code, are overwhelmingly rated
as “Very helpful” or “Extremely helpful” (Figs. 5 and 7), and are de-
signed to provide a complete overview even when shown without
code (Fig. 2b, e.g., in a code search UI). App. B has further discussion
including a taxonomy of different forms of code explanation.
NL outlines are not intended to do any of the following: docu-
ment all details about the code (providing too much information
would reduce efficiency), educate developers about concepts or
APIs (developers can look up tutorials or documentation elsewhere
as needed), provide complex reasoning (some comments are too
important or complex to relegate to AI, including documentation
of tricky implementation or design details), or replace code entirely
(code remains the source of truth considering the ambiguity of NL).
3 Use Cases for NL Outlines
The broad applicability of NL outlines is a key factor in their appeal
as a surface for human-AI interaction. Here we provide an overview

of many potential use cases as illustrated in Fig. 1. A full evaluation
of each use case is beyond the scope of this paper—instead, Section 5
evaluates the common first step of generating NL outlines to begin
with, and Section 6 explores two concrete applications in practice.
Code understanding and navigation. Fig. 3 is a mockup
of how NL outlines could be used in an IDE. NL outlines can be
shown in the list of symbols to aid whole-file understanding while
being clickable for precise navigation. Outlines can also be shown
in the main editor interleaved with the code, assisting with rapid
code understanding and offering intuitive code folding [25 ]. The
user experience can be enhanced through customization of outline
styling, and IDE shortcuts can show or hide outlines, generate new
outlines, convert between outlines and comments, and jump to
adjacent outline statements. NL outlines can be similarly displayed
in other developer tools for code browsing, searching, and so on.
Code maintenance. Once the user is accustomed to using NL
outlines interleaved with code as in Fig. 3, we can apply NL outlines
beyond static (unchanging) code and toward code maintenance.
For example, the IDE can detect when the user is editing a func-
tion. When there is a lull in typing, the IDE may automatically
update the outline to reflect the current code. (This can be done by
providing an LLM with the old code, old outline, and current code,
and prompting the LLM to predict an updated outline.) Some users
may prefer that outlines are updated automatically with minimal
friction, while others might explicitly request an outline update
through a keyboard shortcut and review a diff of the predicted
changes. Either way, this use case resolves a common issue of com-
ments becoming stale as the code evolves [ 51 , 64], lifting the burden
of tedious updates (and constantly checking if any comments need
updating) from the user and delegating it to the LLM. Hence, NL
outlines can serve as automatic living documentation of the code.
We can also perform updates in the reverse direction. If NL
outlines are themselves editable by the user, then the user may
specify the high-level idea of a code change simply by editing the
outline, letting the LLM predict the corresponding code changes.
This concept is quite flexible: edit an outline statement to convey
a minor logic change in that portion of the code, add new outline
statements to guide a multi-line suggestion of new code, reorder
outline statements (potentially outside the function’s boundaries)
for a refactoring that handles dataflow dependencies better than
mere copy/paste, and delete outline statements for a code cleanup
that also removes resulting dead code elsewhere. This would allow
developers to program primarily through natural language, as if
developing high-level pseudocode that is automatically synced to
real code (but we still encourage careful review of the LLM’s code).
We can actually generalize the two previous ideas (where the
user makes a complete edit to the code or outline, and the LLM
only updates the other to match). Instead, we can let the user start
any change(s) (to the code or outline) and have the LLM finish
the change(s) (modifying the code and outline as needed). Many
code changes start with one key idea and then require propagating
changes to code and documentation elsewhere. With this feature,
the user only needs to specify the main idea of each desired change,
and the LLM can perform the more tedious work of implementing
and propagating the change. This may increase developer efficiency
by allowing them to think at a higher level of abstraction and
delegating the lesser details (with careful review). The user can edit
the outline for broad ideas or edit the code to specify more exact
changes, seamlessly switching between code and NL as needed, as
in the literate programming paradigm but with a novel bidirectional
connection between NL and code powered by modern LLMs.
We built this into a prototype Finish Changes feature in an IDE
by providing the old code, old outline, current code, and current
outline to an LLM which then predicts the new code and new
outline. Fig. 4 shows screenshots with real predictions from Gemini
1.5 Flash. In Fig. 4a, editing a variable assignment causes updates
to its description in the outline and its type throughout the code.
In Fig. 4b, replacing one word in the outline causes a multi-line
implementation change and a docstring update. Chain-of-thought
(CoT) prompting [ 63 ] is quite effective here, where the LLM lists the
user’s changes, reasons about further edits to finish those changes,
and lastly predicts the new code with new outline interleaved.
Code generation. The standard approach to function gen-
eration is to take a specification (e.g., the function signature and
docstring) and predict the entire body, but it can be difficult to
understand incorrect or unexpected predictions. The user might
even discover that the prediction is so wrong that they delete it and
start over, having wasted their time completely.
Instead, as previously mentioned, users can write new outline
statements to steer code generation using a Finish Changes feature.
But when writing an entire new function, we can further assist
users by having the LLM propose an NL outline (displayed without
code) for the user to approve before proceeding—an easier task
than writing an outline from scratch or reviewing predicted code
directly [43 ]. The LLM may also predict multiple outlines with
different approaches or interpretations for the user to brainstorm
with. The user may edit an outline to correct mistakes instead of
debugging the code later. By having the LLM generate code aligned
with a user-approved outline, we increase the likelihood that the
code satisfies the user, and it is also easier for the user to interpret
the code because they already expect the outlined approach.
Code review. During code review, a key part of software de-
velopment [13, 56 ], NL outlines can help reviewers understand code
written by others. For example, if NL outlines are automatically
updated to reflect code changes, then the outline changes form an
NL summary of the code changes. Reviewers may then inspect a
diff of the old versus new outlines in addition to the code diff.
Code search. Code search systems in practice mainly use
structured forms of search [ 2, 57 ], but users sometimes do not
know the needed keyword or regex. NL outlines may enable or
enhance more intuitive text-based search: after generating and
indexing NL outlines, a search query containing NL and/or regexes
could be matched to outlines and/or code. Users could then search
for concepts, e.g., to find usage examples or where a particular
action occurs in an application. NL outlines can also provide helpful
context around search results, whether for NL queries, traditional
regex queries, or even symbol references and function call sites.

approach is the possibility that the model changes the code against

the original code, the outline might not describe the original code
anymore. Minor deviations (e.g., changes to blank lines and existing
comments are common) can be ignored if the model gets back on
track, but in extreme cases the outline must be discarded.
This issue can be remedied with the Constrained Generation
approach, using constrained decoding [ 39 , 65 ] to alter token prob-
abilities in a way that prevents changing the code. Specifically,
we construct a regex-like constraint that repeats the code exactly,
except with optional comment lines between code lines. App. D
discusses additional heuristics and implementation difficulties.

Generation and Constrained Generation is that they spend output
tokens repeating the code, leading to unnecessary cost and latency.

model to output a sequence of outline statements, each containing
the line number where the outline statement should be added, and

6 Case Studies
We present deep dives into two concrete applications.
6.1 Android Security
We consider the problem of assessing the security and privacy of
Android applications (or apps). These assessments are performed
routinely by online app stores such as Google Play and Samsung
Galaxy Store, where apps submitted by developers across the world
are analyzed for compliance with policies
6 
meant to protect app
users, e.g.: Apps that are deceptive, malicious, or intended to abuse or
misuse any network, device, or personal data are strictly prohibited.
Determining whether an app is deceptive or malicious involves
understanding the code and relating its functionality to the app’s
description, UI, and user expectations. There are millions of apps
in stores and tens of thousands of new apps added per month, so
security assessments must be efficient.
To detect malicious apps, reverse engineers (REs) use static and
dynamic program analyses to flag code as potentially problematic
and then confirm violations through manual review. The initial
challenge is in the volume of code: many apps have millions of lines
of code, thousands of classes, and complex event-driven execution
paths. Furthermore, an app’s source code is usually not available,
so REs inspect decompiled code which is difficult to understand
for several reasons. Decompiled app code is unnatural due to the
compilation process performing optimizations (e.g., inlining code
and changing code structure) and removing code artifacts (e.g.,
comments, docstrings, types, variable names, and names of inlined
API constants). App code may be further transformed by minifica-
tion to reduce app size [ 4] and obfuscation to protect intellectual
property [1]. Nevertheless, REs must quickly understand the code
to find policy violations—a promising application for NL outlines.
Applying NL outlines. We collected a dataset of 80 decom-
piled functions from real Android apps. Half were manually cu-
rated “suspicious” functions that REs had previously flagged as
using malware techniques, and we focused on including a variety
of techniques and avoiding similar code. The other half were “be-
nign” functions randomly sampled from 8 popular apps assumed
to be malware-free, all from different companies and genres. All
dataset functions have between 24 and 99 lines of code, and we
tried to make the two halves of the dataset have similar distribu-
tions in code length and style (minified or obfuscated) as much as
reasonably possible to reduce bias.

6.2 Code Review
This application is motivated by a common pain-point in code
review: the difficulty in reviewing large or complex change lists
(CLs). With increasing CL complexity, it becomes increasingly dif-
ficult to maintain a complete mental model of all of the changes
and how they interact. This software development anti-pattern is
so substantial that code reviewers may even send large CLs back
to the authors to be split into smaller CLs that are individually
more manageable. Reviewers actually spend much less time per
line reviewing large CLs, raising potential concerns about fatigue
and review quality. Although tools have been developed to assist
in moving code changes between CLs, actually splitting a CL is
time-consuming, and in some cases it might not be possible if the
changes are particularly entangled. So, the burden often falls on the
reviewer to mentally disentangle messy CLs during code review.
We address this with a prototype feature called Virtual CL Split,
which is a layer in an existing code review interface that allows
a reviewer to view individual code changes grouped into logical
topics. Each topic is described with a natural language phrase that
helps the reviewer interpret the changes. The topics form a partition
of the original CL, but this splitting is done virtually, i.e., the CL
itself is unchanged and there is no requirement that any individual
topic can become a standalone CL. Upon selecting a topic in the UI,
all changes in that topic have their code diffs expanded and other
changes are collapsed (or shown with muted diff highlighting when
the reviewer wants to see more file context), so that the reviewer

can focus on the selected topic to simplify their mental stack. Virtual
Split ensures that every code change appears in some topic, so that
the reviewer is “done” after examining all topics. App. I shows

For example, consider a CL where the author first performed a
refactoring causing multiple small changes. This enabled the author
to implement a complex new function and add unit tests for it. Fi-
nally, the author invoked a code formatting tool causing whitespace
changes. In this CL, a Virtual CL Split may suggest 3 topics: first
the new function with its tests, then the refactoring, and lastly the
whitespace changes. The first topic enables the reviewer to inspect
the new function and its tests together (without unnecessary search-
ing or scrolling even though they come from different files), and
the topic description summarizes the new functionality. This is the
most important part of the CL, so it is shown first to improve review
quality [ 14]. Afterward, the second topic helps the reviewer inspect
the refactoring without distraction from whitespace changes, which
are in the last and least important topic.
To generate a Virtual Split, we first provide the CL description
and all file diffs (in unified format) to an LLM to generate a list of
topics with few-shot prompting. Then, for each file in parallel, we
provide the CL description, the diff with line numbers prepended,
and the list of topics. With few-shot prompting, the LLM generates
an NL outline of the diff using the Line Number Infilling technique,
except that the NL outline partitions and describes code changes
(instead of code functionality), and for each diff section, the model
also predicts which topic it belongs to. The resulting diff section
boundaries and topic assignments thus form the Virtual Split. We
highlight that this is an example of how NL outlines can serve as a
foundation for features with very different objectives and UX.
Evaluation. In a preliminary market fit study, we worked
with four software engineers from the same team to evaluate how
often CLs are complex enough to benefit from virtual splitting, and
how often the predicted splits were useful. We randomly selected
73 CLs submitted in their team over the prior weeks with more
than 10 lines changed. Many of these were too simple for virtual
splitting to be helpful, including CLs that were still very short,
CLs which cannot reasonably be split further, and CLs with mostly
deletions, generated files, or rollbacks. Overall, 24 (33%) of the CLs
were deemed complex enough for a virtual split to be helpful. At
the scale of a large software company, this is a huge opportunity to
help reviewers facing complex CLs. We generated virtual splits, and
among the 24 complex-enough CLs, 14 splits (58%) were described as
useful during review. We also observed the pattern that, if the CL is
complex enough and the split was rated as high-quality (i.e., changes
were correctly assigned to topics), then the split was almost always
considered useful, indicating that the concept is well-designed.
After the preliminary study, we improved split quality via prompt-
ing improvements, e.g., summarizing each diff as chain-of-thought
reasoning before generating topics, better utilizing Gemini’s long
context, providing “hints” of line numbers where blocks of changes
start, and adjusting few-shot examples and instructions. In a small
experiment on 10 CLs, these changes noticeably improved split
quality for 7 CLs and only decreased quality for 1. We also used a
newer LLM and made other UX and infrastructure improvements,
and launched the feature to a beta group of about 7000 users on
live code review traffic. Examples of positive user feedback include:
“Is this a new feature? It seems to parse the CL description,
breaks it down into small individual tasks/features and then

“Because the CL was split into 3 tasks, it was easier for me to

between files a lot more especially for large CLs.”
“I saw a CL getting split up into topics in Critique. Simply

Negative feedback mainly expressed that the CL was already simple
enough to be easily understood without a split, so we are working
to better detect these cases preemptively.
7 Discussion
We discuss practical considerations that arise when integrating NL
outlines at scale, ways to improve outline generation, using outlines
within LLM pipelines, and limitations.
Verifying outlines. When paired with feedback mechanisms,
NL outlines can become a resource shared across developers. For
example, thumbs up/down feedback can be collected, and with
sufficient thumbs down, an outline may be hidden or regenerated.
Enough thumbs up can cause an outline to become “verified” and
displayed in a special way (e.g., with a checkmark) signaling that
this outline has approval from other humans. Trusted developers
such as code authors, code reviewers, and project leads may be given
outsized power to influence outlines, e.g., unilaterally marking an
outline as verified. Trusted developers may also be allowed to edit
outlines to correct mistakes (with the edits shown to everyone else),
increasing the quality of outlines and users’ confidence in them.
However, verifying NL outlines takes time and effort, which
must be considered alongside the quality and confidence benefits
of having verified outlines. We emphasize a philosophy of making
things easier for developers in the long run. NL outlines as a concept
may be more or less helpful for different teams, depending on what
they do (e.g., writing new code versus maintaining existing code,
or building standalone projects versus frameworks with users),
the technology and concepts used (e.g., custom APIs that confuse
the LLM), and simply personal preference of team members. A
team may reasonably decide that reviewing NL outlines should be
completely optional. Ultimately, developers should not be given
more work that they think is not worthwhile. We also emphasize
that the code is the source of truth: it is what the computer runs, and
NL is inherently ambiguous. Further research is needed to measure
the perceived and actual benefits of NL outlines used at scale in the
various ways proposed, which should then guide decisions around
tooling, UX design, and team culture.
Comments or metadata? When building NL outlines into
prototype IDE features, we encountered a major implementation
decision: should outlines be stored in the source code as comments
with a special syntax, or as non-code metadata that is stored and
manipulated separately from code? We discuss these options from
the perspective of a large software company.
Storing outlines as non-code metadata has drawbacks mainly
in the difficulty of implementation: the metadata files or databases

must be managed, each developer tool would need to load or edit
the metadata in addition to source code and have a custom UI
layer to support displaying or editing outlines, and implementation
differences may reduce portability and compatibility.
Alternatively, if NL outlines are to be inserted into code as com-
ments, then they should use a special syntax to distinguish them
from other comments, so that readers can treat AI-generated com-
ments with appropriate caution. We propose the star comment
syntax as in Fig. 2c. This is simply a regular line comment but
with an asterisk after the comment syntax, e.g., #* or //* for
most common programming languages.
12 
The asterisk is chosen
to mimic the stars commonly found in AI-related icons such as for
Gemini and GPT-4, while being ASCII and standard on keyboards
(hence compatible with code). Verified outlines may be shown with
syntax like #*! indicating that the comment is more trustworthy.
Programmers and developer tools should follow two basic rules
about star comments: (1) Star comments are usually AI-generated
and should be trusted cautiously, and (2) It is expected that star
comments may be changed, added, or removed by AI tools.
Adding NL outlines into code as star comments leads to a rel-
atively simple integration of NL outlines into developer tooling.
There is no need to update programming language parsers because
star comments are already comments, and similarly no need for
metadata outside the source code file. By default, IDEs and other
developer tools would display star comments in the same way as
regular comments except distinguished by the asterisk, but it would
also be simple to adjust their syntax highlighting. Star comments
are maximally portable because the syntax is not specific to any
developer tool or implementation. Users can add, remove, or edit
star comments in the same way as editing other code. Users can also
convert between normal comments and star comments by adding
or deleting the star to allow or prevent AI updates to that comment.
IDEs may offer keyboard shortcuts to perform some of these ac-
tions. However, star comments have important downsides in churn,
flexibility, and distraction, discussed in more detail in App. J.
Improving outlines. In this work, we generate NL outlines
of a function 𝑓 only from 𝑓 ’s code and few-shot examples, but
providing more context through retrieval-augmented generation
(RAG) [ 27, 41 , 49] may improve the predicted outline’s quality.
For example, one may provide the LLM with the file containing
𝑓 , unit tests for 𝑓 , functions that call or are called by 𝑓 , and even
design documents describing the need for 𝑓 . Similarly, few-shot
selection [ 11 , 26 ] can choose few-shot examples that are the most
similar to 𝑓 , e.g., considering the programming language, kind of
function (unit tests, instance methods, etc.), and so on.
Finetuning is another technique to improve outline generation
quality, using data collected through various means. One can mine
outline-like comments from existing code, but many such comments
are low-quality or incomplete (i.e., only part of the function is
outlined), and we found it difficult to detect such cases at scale.
Another approach is to sample outlines and keep those that score
well on LLM-based evaluation metrics [ 10 , 36 ], but this approach is
limited by the model’s ability to generate a good outline in the first
place. A promising direction could be to use real feedback gathered

Helping LLMs. Sections 5 and 6.1 show that NL outlines are
very helpful to humans—can they also help LLMs? Indeed, NL
outlines as an intermediate step can potentially improve LLM per-
formance on downstream code-related tasks. For example, the case
study in Section 6.2 generates outlines to summarize code changes
in individual files, so that a subsequent prompt can reason about a
multi-file change without being overwhelmed. Similarly, App. K de-

Limitations. In Section 5 we used 6 survey participants, and in
Section 6.2 we used 4 participants from one team, so those findings
may be specific to those participants. As described in Section 5, the
30 dataset functions were not sampled uniformly. In practice, many
functions are boilerplate, very short or simple, or otherwise less
interesting, making it less likely that a developer would read an NL
outline for that function anyway. Instead, we focused on dataset
variety and choosing interesting functions (and only in Python
which is our expertise). Our choice of functions can introduce bias.
8 Related Work
Code summarization has attracted much recent attention [ 7– 9, 17,
22 , 30 , 34 , 47 , 60 , 66 , 68 ]. App. B presents a taxonomy contrasting
the many forms of code explanation. NL outlines are one such form,
but instead of a standard paragraph, an outline is written as a list
of statements that can be aligned to and interleaved with the code.
Moreover, most methods of code summarization have not been
applied to the many use cases of NL outlines (Section 3).
Some related works do consider individual use cases, e.g., Pan-
thaplackel et al. [ 51 ] aim to update comments given code changes
using a custom bidirectional GRU, but NL outlines accomplish this
through LLM prompting and generalize to the reverse direction
of updating code given outline changes. Liu et al. [ 43 ] present a
technique for code generation from NL where the generated code
is summarized to assist the user in writing future prompts, but
they do not consider applications beyond code generation. Code
folding [25 ] can provide a quick overview of code, and NL outlines
extend this idea by providing intuitive folding locations and NL
summaries of the folded code. A key contribution of NL outlines is
their general applicability toward all of these use cases and more.
LLMs have been broadly applied to software engineering [ 24 ,
33 , 59 , 67 ], including integrating LLMs into IDEs to provide coding
suggestions [3, 53 , 61 ], chat assistance [ 45 , 55], educational infor-
mation [ 44 , 48 ], and novel coding experiences [ 12 , 18]. NL outlines
offer a different approach to incorporating AI into developer tools.
9 Conclusion
Natural language outlines are a new form of code explanation that
summarize the main ideas for rapid understanding. Our experi-
ments show that LLMs can generate accurate and helpful NL out-
lines in practice. We describe the huge potential to use NL outlines
to assist software developers in numerous ways, and we call for
further research to advance these transformational ideas.

B Taxonomy of Code Explanation
NL outlines are a novel way of explaining code with different ben-
efits and drawbacks compared to other types of code explanation
like docstrings and tutorials. To clarify the distinctions, we can
classify types of code explanations by:
(1) 
Topic: It may primarily explain the interface of some code,
its implementation, the design decisions it required, details
of APIs and concepts involved, etc.
(2) Audience: The target readers could be novice programmers,
experienced developers, maintainers of the code, users of an
API, project managers, etc.
(3) Location: Explanations can occur within code like names
and inline comments, in a separate document like a design
document or bug report, within developer tools like IDEs or
code search interfaces, in Web sites like Javadocs, ephemerally
in conversation with an LLM chatbot, etc.
(4) 
Length: Effective explanations can be as short as a single
symbol like a well chosen method name, or much longer like
a sentence, paragraph, or even a book.
NL outlines occupy a particular space within this taxonomy.
In terms of topic, NL outlines focus on the implementation strat-
egy: the high-level steps taken to achieve the function’s goal. The
audience comprises experienced developers who wish to write,
maintain, or build upon the code. NL outlines would primarily be
shown within code and in developer tools. Finally, an outline is a
list of sentence-length statements which in total are much shorter
than the code they describe.
This helps distinguish NL outlines from other forms of code
explanation. For example, docstrings focus on the contract of a
function and its usage instead of the implementation [31 ], and are
more often read by API users than code maintainers. Pseudocode
is more literal than NL outlines (e.g., explicitly providing every
variable update instead of abstracting out the broad concepts) and
usually appears in textbooks [20 ] and rarely in professional software
projects. LLM explanations also vary widely depending on the user’s
prompt [ 48 ], but they are often ephemeral and long explanations
going into great detail to help novices and developers unfamiliar
with the concepts involved, unlike the concise format of NL outlines
which persist in the code or developer tooling. Design documents
are a longer form of code explanation, aiming to describe a software
architecture including constraints on the design and alternatives
that were considered [ 23 ], ultimately presenting a different set
of information for a different audience (e.g., project managers)
compared to NL outlines.
At first glance, NL outlines may seem similar to inline code
comments, especially because NL outlines may be displayed like
comments. Interestingly, Scalabrino et al . [58] measured how code
understandability correlates to various metrics including the pres-
ence of comments, but ultimately obtained a negative result: the
number of comments was not correlated with perceived or actual
understanding. We take this as evidence that the style of com-
ments typically written by developers is not optimized for code
understanding—developers usually write sporadic comments about
pitfalls, developer intent, and reminders for future work [ 52 , 54 ],
without summarizing the functionality more completely. In con-
trast, our NL outlines focus on the high-level ideas in the function’s
implementation, are written in a way that still makes sense when
presented without code, and are designed to boost code understand-
ing (e.g., overwhelmingly rated as “Very helpful” or “Extremely
helpful” in Figs. 5 and 7).
C Finish Changes with Multiple Changes
Section 3 describes using NL outlines for code maintenance, in
particular suggesting a Finish Changes feature which allows the
LLM to finish any changes the user has made to the code or outline.
Fig. 4 illustrates two example usages of the Finish Changes feature,
each involving one conceptual edit. But actually, Gemini 1.5 Flash is
powerful enough to handle multiple changes at once: Fig. 8 shows
a successful implementation of three simultaneous changes.
In our experience, the Finish Changes feature with Gemini 1.5
Flash can suggest surprisingly good edits, but it is not always per-
fect. The likelihood of slight mistakes tends to increase with more
changes requested simultaneously, or if one change requires prop-
agating many different kinds of edits to different locations. We
observed that the most common mistake is an incomplete propaga-
tion of changes that lacks some necessary downstream edit. But,
this also means that most of the suggested changes are on the right
track.
Gemini 1.5 Flash occasionally suggests an “improvement” that
is not strictly needed to finish the user’s changes, such as adding
more detail to a docstring which was not made stale in the first
place. The actual suggestions are usually very reasonable, but this
behavior may be distracting to users.
We chose to explore the Finish Changes feature with Gemini 1.5
Flash due to its low latency—we receive predicted diffs in about 5
seconds, allowing developers to iterate on code quickly.
D Constrained Generation
Recall from Section 4 that Interleaved Generation has the drawback
of potentially changing the code against our wishes, resulting in
predicted outlines that no longer apply to the original code. Our
Constrained Generation approach resolves this issue by using con-
strained decoding [39 , 65 ]: we construct a regex-like constraint that
forces the model to repeat the code exactly, except with optional
comment lines between code lines. If the original code parses, we
can also require an outline statement before the first line of the
function body (after the function signature and docstring) and pre-
vent outline statements from being added above a blank line or in
the middle of a multi-line statement or comment block. These extra

F Errors when Parsing Outline Predictions
Section 5 and Table 1 mention errors detected while parsing an
LLM’s outline predictions. Here we provide more details about the
specific errors and their frequency.
Here is a list of all errors we checked for when parsing an outline
prediction using the Interleaved Generation technique, including
the severity (major or minor), the frequency in the experiment
(number of LLM predictions where the error occurred, out of 150
predictions considering the 5 models and 30 functions), a descrip-
tion of the error’s meaning, and what we do when encountering
the error:
• Extra blank line (minor, 19 predictions): When perform-
ing a top-down line-by-line comparison of the predicted code
with outline versus the original code (i.e., searching for added
comments which form the interleaved outline), we encounter
a blank line in the prediction where the corresponding line in
the original code is not blank (lines containing only whitespace
are also considered blank). We simply skip the blank line in the
prediction, as if it did not exist.
• Missing blank line (minor, 7): When performing the same line-
by-line comparison as described above, we encounter a blank
line in the original code where the corresponding line in the

prediction is not blank. We similarly skip this line in the original
code, as if the prediction did contain a matching blank line.
• 
Consecutive comment (major, 0): We encounter multiple con-
secutive comment lines present in the prediction but not in the
original code. We concatenate the text of the comments into one
outline statement, just in case the model decided to split a long
comment onto multiple lines, but the long comment length likely
indicates poor quality.
• 
Missing comment (minor, 20): We encounter a comment line
in the original code where the prediction does not have a corre-
sponding match. We simply skip this line in the original code,
as if the prediction did contain a matching comment.
• Changed trailing comment (minor, 1): We encounter corre-
sponding lines in the prediction and original code that do not
match, and neither is a blank line or comment line, and they do
match if we ignore trailing comments. We simply move on, as if
the prediction’s trailing comment did match the original code’s
trailing comment (if any).
• 
Changed code (major, 10): We encounter corresponding lines
in the prediction and original code that do not match, and none
of the prior cases apply. We stop processing the prediction and
return any outline statements already parsed, because any fur-
ther outline statements are for predicted code that has deviated
significantly from the original code.
• Extra prediction lines (minor, 0): We matched all lines in the
original code to corresponding lines in the prediction, but the
prediction still has unmatched lines remaining. We ignore those
lines, as if the prediction stopped in accordance with the original
code.
• Missing prediction lines (major, 0): We matched all lines in
the prediction to corresponding lines in the original code, but the
original code still has unmatched lines remaining. The predicted
outline is likely incomplete since the prediction stopped early,
but there is not much we can do about it (without another LLM
query).
• 
Empty outline (major, 2): After the parsing process, the outline
contains zero outline statements. This is clearly a poor prediction,
but there is not much we can do about it.
Although the Constrained Generation technique is not used in
our experiments (Section 5), its predictions are formatted like those
for Interleaved Generation. Hence, we use the same procedure to
parse the LLM predictions and detect errors (although some are no
longer possible due to the constraints).
Here is an analogous list of errors we checked for when using
the Line Number Infilling technique:
• 
Malformed line (major, 1 prediction): The prediction line
does not follow the expected format of line number, separator,
and outline statement. We skip this line.
• Line number out of bounds (major, 0): The line number is
smaller than 1 or greater than the number of lines in the original
code. We skip this line.
• Not sorted (minor, 0): The prediction lines were not sorted by
line number in ascending order. We sort the lines.
• Duplicate line number (major, 0): The prediction contained
multiple lines with the same line number. We keep the first
instance and ignore the latter duplicates.
• Commented empty line (minor, 6): A line number actually
points to a blank line in the original code. Since it is unnatural to
add a comment above a blank line (the blank line should go above
the comment, which is then directly above its section of code),
we increase the line number such that the outline statement is
placed above the next non-empty line.
• 
Empty outline (major, 0): After the parsing process, the outline
contains zero outline statements. This is clearly a poor prediction,
but there is not much we can do about it.
G Quality Survey Questions
Section 5 and Fig. 5 refer to a survey we used to gather human
opinions about NL outline quality. In total, we obtained 300 outline
predictions: 30 functions in the dataset × 5 LLMs × 2 generation
techniques. For each function, we asked the contributor of that
function to inspect the function’s 10 predicted outlines, which were
presented in shuffled order without any labeling of which LLM
or technique produced that outline. For each outline, the function
contributor answered five survey questions with multiple-choice
answers, listed below. Survey participants were also given a docu-
ment containing clarifications to the questions, also listed below.
(1) How good is the outline overall, relative to an optimal outline
for this function?
→ Excellent / Good / Acceptable / Bad / Terrible
• This question measures the room for improvement in the
LLM predictions.
• Don’t judge the broad concept of NL Outlines, or that out-
lines may be fundamentally less useful for certain kinds of
functions. Instead, judge the outline sample relative to the
best outline you can think of for that function. How close is
this outline to being the best it can be for that function?
• The factors in the other questions (helpfulness, correctness,
detail, style/fluency) may factor into your judgment for this
question. How much to consider each factor is up to you, so
that you can judge the outline holistically.
• As a point of reference, a completely empty outline should be
considered “Bad”. Note that a “Terrible” outline can be worse
than this, if it ends up being a big waste of time (e.g., a lot
of words that are obviously nonsense, or a convincing but
incorrect outline that leads to future bugs).
(2) How helpful would this outline be in practice?
→ Very helpful / Somewhat helpful / Not helpful
• 
This question measures the practical utility of the outline,
relative to the baseline of not having outlines at all.
• How helpful would this outline be to developers in general,
including the code author and other developers who may
have varying amounts of familiarity with the code?
• 
Consider the purpose of NL Outlines and multiple potential
use-cases, as described above.
• You may consider that some functions (e.g., very simple func-
tions) might naturally benefit less from outlines.
• Assume that readers of the outline understand that it is AI-
generated and may be incorrect, and they act reasonably with
that understanding. The amount of trust they have in the
outline may depend on how convincing the outline seems,
within reason.

def parse_prediction (

) -> ParsedPrediction :
""" Extracts ( summary , suspicion score , outline , errors ) from
the response . """
#* Handle the case where the prediction contains extra text.
if '\n\n\n ' in prediction :
prediction = prediction . split ( '\n\n\n ')[0]
errors = []
#* Parse the prediction based on the prompt strategy.
if prompt_strategy == ' summary_verdict_outline ':
#* Check for missing sections and return an error if any are found.
if '\n\ nSuspicion score :\ n ' not in prediction :
errors . append ( '[ no score section ] ')
if '\n\ nNotes :\ n ' not in prediction :
errors . append ( '[ no outline section ] ')
if errors :
return ParsedPrediction ( summary = '', score =-1 ,
outline =[] , errors = errors )
#* Extract the summary, score, and outline text from the prediction.
summary , _ , remaining = prediction . partition (
'\n\ nSuspicion score :\ n ')
score , _ , outline_text = remaining . partition ( '\n\ nNotes :\ n ')
elif prompt_strategy == ' outline_summary_verdict ':
raise ValueError ( ' outline_summary_verdict is deprecated . ')
else :
raise ValueError (
f ' Unhandled prompt strategy : { prompt_strategy } ')
#* Clean up the summary, score, and outline text.
summary = summary . strip ()
score = score . strip ()
if score in [ '0 ', '1 ', '2 ', '3 ']:
score = int ( score )
else :
errors . append (f '[ unexpected score : { score }] ')
score = -1
outline_text = outline_text . strip ()
#* Parse the outline text into a list of tuples containing line numbers and comments.
outline = []
if outline_text != '<None > ':
for line in outline_text . splitlines ():
match_result = re . fullmatch (
r '^ Lines ? (\ d +)(?: ?- ?\ d +)?: (.*) $ ', line )
if not match_result :
errors . append ( '[ malformed outline line ] ')
continue
line_number = int ( match_result . group (1))
comment = match_result . group (2)
outline . append (( line_number , comment ))
#* Sort the outline by line number and check for duplicate line numbers.
outline = sorted ( outline , key = lambda pair : pair [0])
i = 1
while i < len ( outline ):
this_line = outline [i][0]
last_line = outline [i -1][0]
if this_line == last_line :
errors . append (f '[ duplicate line number : { this_line }] ')
outline . pop (i)
else :
i += 1

summary_lines = summary . splitlines ()

I Virtual Split for Code Review
Section 6.2 discusses the Virtual Split feature which helps code
reviewers tackle complex change lists (CLs). Here we provide illus-
trative screenshots, lightly edited for clarity and space.
Fig. 17 shows an example CL in Critique, Google’s internal code
review platform. The top area contains metadata about the CL,
including its author, any assigned reviewers, and the CL description
provided by the CL author (in this case, “Add AST height analysis
to python_graphs”). Then, a diff navigation toolbar is provided,
containing a “Expand Diffs” or “Collapse Diffs” button followed by
series of buttons representing topics in the Virtual Split. Each topic
button contains a short description of the topic (e.g., “Analyzed AST
height”) and the percentage of the CL’s changed lines which are
assigned to that topic. The initial state is shown where none of the
topic buttons have been clicked yet. Finally, a table is shown where
each row contains metadata about one changed file in the CL. Each
row is clickable and displays or collapses that file’s diff. In this case,
the diff for BUILD was left collapsed, while diffs for analysis.py ,
analysis_test.py , and run_analysis.py have been expanded.
Without Virtual Split, a CL reviewer would not see any topic
buttons, and they would typically read each file diff from top to bot-
tom, either in the file order listed on screen or using the reviewer’s
intuitions for which files to read first. However, users report that it
is difficult to quickly identify the most important changes to review,
and to simultaneously keep in mind all of the changes happening
within a complex CL (often much more complex than this example).
Fig. 18 shows the state after the user clicks the first topic button,
i.e., “Analyzed AST height”. This automatically expands only the
portions of diffs related to that topic, collapsing unrelated changes
in the file (e.g., the _program_graph_to_nx changes in analysis.py )
or entire unrelated files (e.g., BUILD ). This way, reviewers can focus
on changes within this topic without being distracted by unrelated
changes. For example, the reviewer can see the new ast_height
function in analysis.py , its unit tests in analysis_test.py , and its
usage in run_analysis.py , all adjacent to each other to minimize
scrolling and context switching. Users still have the option to ex-
pand any collapsed diffs to see more context as needed.
Fig. 19 shows the state after the user clicks the second topic but-
ton, “Removed unused code for directed graphs”. This expands
changes to the _program_graph_to_nx function signature, imple-
mentation, and calls in analysis.py . Even though some unrelated
changes in that file are visible within the displayed diff context,
those unrelated changes are highlighted in gray instead of the usual
red/green highlighting. Furthermore, since analysis_test.py is not
expanded, the reviewer can then infer that the _program_graph_to_nx
changes do not come with associated changes to unit tests (assum-
ing that the Virtual Split is accurate).
Our system guarantees that every changed part of every file is
assigned to some topic, so that once a reviewer has clicked through
all of the topic buttons, they have seen all of the changes in the CL.
Furthermore, the LLM tries to order the topics from most to least im-
portant, thus helping reviewers quickly identify and navigate to the
most salient parts of the CL. Overall, the topic descriptions help re-
viewers understand a complex CL at a glance, and the topic buttons
guide reviewers through an organized, focused, and sequentially
prioritized viewing of the changes.

J Drawbacks to Star Comments
Star comments, proposed in Section 7, have important downsides
in churn, flexibility, and distraction.
Churn: Source code is expensive to store and edit considering
the costs of version-controlled storage forever, the human cost of
code review, and extra strain on continuous testing infrastructure.

Putting all iterations of NL outlines (which change alongside the

is thus surprisingly expensive. Alternatively, storing NL outlines as
non-code metadata in a central database or in extra files adjacent
to the source code (but without version control, mandatory code
review, or continuous testing) would significantly reduce churn.
Flexibility: Star comments reduce the flexibility to update outlines
without causing more churn. Even if the code is not changed, it may
still be desirable to update or deprecate outlines due to prompting

Distraction: Star comments in the code are by default visible, like

K Generalizing Outlines to Files and Projects
This paper focuses on NL outlines for individual functions because
code flow within a function is naturally structured: code flows from
top down, excluding control flow jumps. This implies that adjacent
code lines are likely to be semantically related, forming clusters of
related lines. Hence, an NL outline is designed to partition the lines
into those logical clusters.
This is no longer true at the level of a class or file, where code flow
is less predictable without enforcement of an organized ordering of
functions or classes within a file. If functions were well-organized,
then it would be straightforward to partition them into semantic
groups with outline statements, but it is less clear what should be
done if the functions are not organized. Should the LLM suggest a
reordering? That could help keep files more organized but could
also confuse developers unaware of the reordering. Alternatively,
we may create a file outline that is not aligned with the code (and
thus cannot be shown interleaved with the code), e.g., an unordered
mapping of functions to semantic groups. The list of symbols in a
file (provided in an IDE sidebar) typically allows the user to sort
the symbols by code position or alphabetically, and this idea may
suggest a new semantically-grouped ordering where each group is
summarized with an outline statement.
Outlining a project may mean generation of a README file that
summarizes the main ideas, lists important directories and files
and their purpose, and provides examples of usage or application
flow. It may also include generated diagrams illustrating the user
journeys, data flows, class hierarchies, and so on. The outline may
incorporate human-written sections and could be automatically
updated as the code evolves.
We imagine that outlining a file or project likely begins with
generating NL outlines for functions first, and then using those for
further LLM prompting, reasoning, abstraction, and summarization
in a hierarchical manner, and combined with static or dynamic
analyses where applicable. In this sense, NL outlines can be building
blocks in complex LLM pipelines.
