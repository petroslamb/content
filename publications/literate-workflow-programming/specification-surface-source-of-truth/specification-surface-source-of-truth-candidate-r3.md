# The Specification Surface Is the New Source of Truth

The pull request looks normal until the reviewer asks the only question that matters. The agent-generated diff is plausible. The tests pass. The summary explains which files changed and why the change is supposed to work. But no one can point to the maintained statement of what the feature had to preserve, which assumptions were settled, which behavior was out of scope, or what the agent was not allowed to change. The code is visible. The authority behind the code is not. The team is reviewing the downstream artifact while the controlling intent stays outside the governed system.

That is the quieter failure underneath vibe coding. The obvious risk is misplaced trust in a model. The deeper failure is that intent remains informal until generated code becomes the only object treated as real. Once that happens, every later question has to be reconstructed from symptoms. Why did the agent choose this schema? Which constraint was binding? Which test proves the important thing? Which instruction should survive the next model, the next run, or the next developer? A prompt transcript, a vague ticket, or a private design choice may explain the path, but none of them can govern the system unless they become durable, reviewable, and repairable.

The object that repairs this failure is a specification surface. A specification surface is a written surface that gains operational force because it is controlled, maintained, typed, linted, validated, trace-linked, interpreted by a runtime, compiled into tests, or used as the stable artifact against which generated behavior is checked. The syntax is secondary. The decisive property is governance. Loose prose remains loose prose. A README full of advice does not become a control plane by existing in the repository. A one-off chat prompt does not become source of truth because it preceded the code. The surface matters only when the system and the team can act on it.

Spec-driven development makes this larger than an agent-harness niche. The old software problem is familiar: requirements drift, design documents rot, and the implementation becomes the only artifact everyone believes. AI coding raises the pressure because implementation can now appear faster than intent can be rediscovered. Spec-driven development inverts that hierarchy by treating specifications as contracts that code implements, verifies, or derives from. It also gives the argument necessary discipline. Spec-first work uses the specification to guide implementation. Spec-anchored work keeps specification and code aligned through tests, contracts, and review. Spec-as-source makes generated code derivative of a human-edited specification where the tooling and domain can support that burden.

That spectrum blocks the lazy version of the claim. The future is not every team throwing markdown into a repository and calling it source. Spec-first work can drift. Spec-anchored work needs tests, contract checks, and review habits that keep the surface alive. Spec-as-source fits only where generation tooling is mature enough and the domain can tolerate the discipline. The useful rule is enough specification to remove consequential ambiguity, with enough enforcement to make drift visible. Authority comes from the maintenance loop, not from the romance of writing things down.

The hinge of the essay is the specification gap. In "The Specification Gap," multiple code agents independently implement parts of the same class while the shared specification loses detail. When the specification is stripped from full docstrings toward bare signatures, two-agent integration accuracy falls sharply, while a single-agent baseline degrades more gracefully. The result matters because it turns a governance phrase into a coordination failure. Weak specifications remove shared decisions that separate workers cannot reliably infer from their fragments.

The recovery result is even more important. The paper's conflict detector can identify structural mismatches, especially when specifications are weakest, but conflict reports do not replace the missing shared specification in the studied recovery setting. Restoring the full specification is what recovers performance to the single-agent ceiling. Diagnosis explains where the break appears. Specification carries the shared decisions that prevent the break from becoming normal. That is the source-of-truth claim under pressure: when generated parts fail to integrate, better post-hoc inspection is not enough. The governing surface has to contain the decisions independent work must share.

This makes the broader argument less metaphorical. Human teams already know the pattern through API contracts, BDD scenarios, acceptance criteria, architecture constraints, schemas, and interface definitions. Agents make the cost of weak surfaces easier to see because they can generate plausible work faster than organizations can reconstruct intent. The specification gap is the machine-speed version of an old software problem: separate workers do not reliably converge on unstated decisions.

The professional-practice evidence points in the same direction. "Professional Software Developers Don't Vibe, They Control" studies experienced developers using coding agents through field observations and surveys. Its useful contribution is not the slogan. It is the mechanism. Experienced developers use agents for speed while preserving agency over design and implementation. They plan before implementation, supervise outputs, validate changes, use version control, limit how much work an agent does at once, and rely on domain expertise to decide where agents are suitable. They do not treat agent output as autonomous authority.

That finding gives `vibe` its proper role. Vibe is a source-of-truth error. It asks the model to carry intent privately and then asks the generated code to stand as the public record. Professional control moves the burden back into artifacts: plans, specifications, tests, constraints, reviewable diffs, traces, and rollback points. The experienced developer's skepticism is infrastructural. Control has to live somewhere the team can inspect.

The strongest agent-specific papers show how this surface becomes operational. In "Bootstrapping Coding Agents: The Specification Is the Program," the stable artifact is a compact specification that can generate an agent, which can then use the same specification to generate another implementation. The paper does not prove that prose should replace all code. It shows a controlled inversion: the specification is the durable object, and implementations become downstream products that can be compared against it. If they diverge, the repair target is the specification and its interpretation, not the mere fact that a file changed.

"Natural-Language Agent Harnesses" moves from product specification to execution structure. The harness contains decomposition, roles, state, adapters, contracts, verification, and durable artifacts in a form interpreted by a runtime. AgentSPEX pushes the same idea into a typed workflow language with steps, branches, loops, state management, checkpointing, tracing, replay, and verification. These are mature specification surfaces: readable enough for people to inspect, structured enough for tools to parse, and operational enough to shape execution.

The important word remains surface. A surface can be read before execution, acted on during execution, and audited after execution. It has edges. It can be versioned, diffed, parsed, tested, and linked to evidence. A chat prompt vanishes into a session. A maintained workflow file can become part of the system's source. The distinction determines whether the team can tell what changed, who authorized it, what constraints applied, and which failure should force the surface to be repaired.

ContextCov makes the transition from passive instruction to active invariant especially clear. Agent instruction files such as AGENTS.md, CLAUDE.md, or copilot-instructions.md can contain real project guidance, but guidance on the page is weak unless it enters a control loop. ContextCov extracts constraints into executable checks: shell shims, AST queries, architectural validators, and LLM-based judgments where deterministic checks are not enough. The document becomes a source of invariants. Failures reveal not only agent mistakes, but ambiguity, staleness, or drift in the instruction surface itself.

Test-Driven AI Agent Definition and FASTRIC make the same discipline visible at the prompt and interaction level. A natural-language product specification can generate visible and hidden tests, then drive prompt and tool refinement against those tests. A multi-turn prompt protocol can be specified enough to check roles, state transitions, tool use, and procedure. The point is not that stricter form always improves behavior. The point is that the right surface makes behavior inspectable. Formality earns its place when it gives a team something to test and repair.

Trace and audit papers complete the downstream side of the hierarchy. AgentPex evaluates traces for procedural violations that outcome-only scoring can miss. AgentFixer uses validation checks, trace comparisons, root-cause analysis, and repair suggestions to turn failures into refinement pressure. "From Fluent to Verifiable" shows why polished outputs are not enough when claim-evidence relations cannot be reconstructed. These systems are evidence surfaces. They tell the team whether execution respected the specification surface and where the surface failed to say enough.

That distinction matters most for context files. Agent READMEs and repository-level instruction files are real signals that software teams are creating machine-facing project artifacts beside source code. They also expose the trap. More context does not automatically produce more control. A long instruction file can be stale, contradictory, ignored, or useful only for a narrow class of tasks. The evidence supports a disciplined claim: context files can become part of a specification surface when they are maintained and connected to evaluation or enforcement. They remain documentation when they merely explain the project.

The operational test is simple. If a file can change what an agent is allowed to do, what state must persist, which tools are reachable, what outputs count as valid, what tests are generated, which trace violations matter, or what claims can be carried forward, then it belongs near the specification surface. If it only describes the project for human orientation, it may be valuable documentation, but it should not be confused with the artifact that governs AI-assisted work.

Generated code still matters. It is the executable material of the system. It carries bugs, latency, security exposure, maintenance cost, and user consequences. A serious team still reviews it. In AI-assisted work, though, the generated implementation is often the most visible downstream artifact, not the most stable upstream one. A team that treats the diff as the whole truth keeps reviewing symptoms. A team with a maintained specification surface can ask stronger questions: Was the intended behavior specified? Were the constraints checkable? Did the implementation drift from the surface, or did the surface fail to carry the needed decision?

The practical burden is plain. Teams need to decide which surfaces deserve authority. They need to keep those surfaces short enough to audit, structured enough to parse, explicit enough to test, and close enough to execution that violations hurt. They need linting for instruction files, validators for workflow files, regression suites for prompt behavior, trace checks for multi-step runs, contract tests for generated interfaces, and claim ledgers when generated research or planning enters the system. This is where control lives when implementation can be generated faster than intent can be rediscovered.

The frame is not `natural language is code`. Some specification surfaces are written in ordinary language. Some are YAML. Some are markdown with machine-readable conventions. Some are tests, schemas, protocols, trace policies, or claim-evidence ledgers. Their common property is governed authority: they are maintained surfaces that systems read, tools check, humans review, and failures push back into revision.

Return to the pull request. The reviewer can still inspect the code, and should. But the first serious questions now happen upstream of the diff. What surface governed the agent? What evidence shows that the work conformed to it? What missing decision should be added to the surface before the next run? If the answer lives only in a chat transcript, the system is still running on atmosphere. If the answer lives in a maintained artifact that can be read before execution, checked during execution, and repaired after failure, the team has a source of truth. That is the specification surface. That is where AI-assisted software work becomes governable.

## Limits

This candidate does not claim that natural language is code, that generated implementation stops mattering, that every document is a source-of-truth artifact, or that more formal specification always improves model behavior. It also does not claim that every team should adopt spec-as-source. The argument depends on controlled, maintained, validated, typed, linted, trace-linked, or runtime-interpreted surfaces that actually enter a control, review, or validation loop.

The bridge papers support a narrowed public claim. `2602.00180` supports specification authority as a software-practice spectrum, not universal spec-as-source adoption. `2603.24284` supports specification-first coordination under the studied multi-agent code-generation conditions, not a guarantee that full specifications eliminate every coordination cost. `2512.14012` supports professional-control practice among experienced developers, not a claim that every developer already works this way.
