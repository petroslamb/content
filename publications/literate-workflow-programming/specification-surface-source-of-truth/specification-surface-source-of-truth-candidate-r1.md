# The Specification Surface Is the New Source of Truth

Software teams are learning to generate code faster than they can govern the intent behind it. That is the quiet failure hiding inside the cheerful language of vibe coding. The prompt looks like the source of intent, the generated diff looks like the source of change, and the repository accepts the output as if the important artifact has arrived. But the thing that decides whether AI-assisted work can be reviewed, repeated, repaired, and trusted is often somewhere else. It is the maintained surface that tells the machine what kind of work is allowed, what state must persist, what constraints must hold, what tests or traces can invalidate a run, and what a human reviewer is supposed to inspect.

That surface does not become important because it is written in English. Loose prose is still loose prose. A one-off prompt is still disposable. A README full of advice is not automatically an operating system for an agent. The shift begins when a written artifact becomes controlled: typed, linted, validated, trace-linked, interpreted by a runtime, compiled into tests, or used as the stable object against which generated behavior is checked. That is the specification surface. It is the place where human intent stops being private instruction and becomes public machinery.

The old mental model treats source code as the only serious object. Requirements explain it, prompts request it, docs describe it, logs record it, and tests complain when it breaks. AI coding strains that hierarchy because the implementation can now be regenerated, rewritten, or forked by a model at a speed that makes the surrounding intent layer more important, not less. When the generated code is cheap, the governing artifact becomes the scarce one. The question moves from "did the model produce code?" to "what surface keeps this code connected to the behavior, constraints, and review burden we actually meant?"

Martin Monperrus's "Bootstrapping Coding Agents: The Specification Is the Program" pushes this question into its cleanest form. The experiment starts from a compact natural-language specification of a coding agent. A first agent implements it. The resulting agent then uses the same specification to implement the agent again. The paper's point is not that every program should be replaced by prose. Its sharper claim is that, in this controlled setup, the stable artifact is the specification. The implementations are downstream products. If they diverge, the error is not repaired by admiring the generated files. It is repaired by auditing the specification that every implementation consumes.

That inversion matters because it changes where correctness lives. In ordinary code review, the diff is the obvious artifact of record. In AI-native work, the diff may be a build product from a higher-level source. The durable review question becomes whether the specification completely and unambiguously describes the intended behavior, whether independent implementations converge, and whether the surface is small enough to audit. Generated code still matters. It runs in production, carries bugs, creates security exposure, and gives reviewers concrete evidence. But it no longer has to be the only object treated as source.

The same pattern appears when the artifact is not a product specification but a harness. "Natural-Language Agent Harnesses" argues that the logic surrounding an agent often dominates outcomes: decomposition, contracts, roles, state, adapters, verification, and durable artifacts. In many systems that logic is buried in controller code, framework defaults, shell scripts, and tacit runtime assumptions. The paper's Natural-Language Agent Harness makes that layer explicit as an executable object interpreted by a shared runtime. The useful move is not poetic. It is architectural. Harness policy separates from runtime policy, state becomes path-addressable, contracts become inspectable, and stage structure becomes something a human can review before the next run.

AgentSPEX makes the same claim in a more structured language. It defines agent workflows in YAML with typed steps, branching, loops, reusable submodules, explicit state management, checkpointing, tracing, replay, and verification. This is exactly what a specification surface looks like when it matures: a written artifact that is readable enough for domain authors, structured enough for tooling, and operational enough for an interpreter. The source of behavior is no longer hidden inside a Python control loop. The workflow itself becomes the object that can be inspected, modified, validated, replayed, and compared.

The important word is not "natural." The important word is "surface." A surface can be read by a person and acted on by a system. It has edges. It can be versioned, diffed, parsed, linked, and checked. A prompt in a chat box has almost none of those properties. A maintained agent workflow file does. A behavioral test specification does. A constrained prompt protocol can. A typed harness file can. A markdown instruction file might, but only if it is tied to enforcement or evaluation. The distinction is the whole essay.

ContextCov is useful because it refuses to let agent instructions remain passive text. It starts from files such as AGENTS.md, CLAUDE.md, or copilot-instructions.md, then extracts constraints into executable checks: shell shims for process rules, AST queries for source patterns, architectural validators for structure, and LLM-based judgment where semantic constraints cannot be made deterministic. The paper names the central gap clearly. Instructions can be adequate on the page and still fail under execution because an agent prioritizes task completion, follows existing code over documented guidance, or ignores constraints buried in long context.

That is why the answer cannot be "write better instructions" in the abstract. Better instructions matter only when the instruction surface enters a control loop. ContextCov turns the document into active invariants. It also creates a feedback path back to the instruction file itself: false positives, false negatives, and constraint drift reveal where the instruction is ambiguous or outdated. At that point the document is no longer a passive supplement to the codebase. It is an artifact with tests, failures, and maintenance pressure.

Test-Driven AI Agent Definition supplies another version of the same pattern. A natural-language product specification is converted into visible and hidden tests. A second agent refines the prompt and tool configuration until the visible tests pass. Mutation testing and spec-evolution scenarios measure whether the result is robust or merely tuned to the visible suite. Again, the lesson is not that prompts are magic source files. The lesson is that prompt behavior can be governed when specifications compile into tests, when hidden cases measure overfitting, and when changes are judged against regression safety. The specification surface earns authority by generating checks that survive contact with candidate behavior.

FASTRIC pushes that logic into multi-turn interaction. Its concern is not whether an answer sounds good, but whether an interaction follows the intended protocol across stateful turns, roles, tools, and procedure. It frames specification formality as a design variable: enough structure to verify conformance, not so much ceremony that the model's instruction-following strengths are wasted. This caveat is important. More formality is not automatically better. The right surface is the one that makes the intended behavior inspectable and checkable for the task at hand.

Trace papers make the downstream half of the hierarchy visible. AgentPex extracts behavioral rules from prompts and system instructions, then evaluates agent traces for violations that outcome-only scoring misses. A customer-service trace can end in the correct database state while violating procedure along the way. AgentFixer broadens the validation plane with input checks, output checks, cross-stage consistency checks, trace comparison, root-cause analysis, and refinement recommendations. These systems matter because they show why run logs are not the source of truth. They are evidence. They tell you whether execution respected the specification surface, where the surface was incomplete, and what must change before the next run.

The same distinction appears in claim-level auditability. "From Fluent to Verifiable" argues that deep research agents need more than action logs or polished reports. They need claim-evidence relations that preserve what supports what, where contradictions remain, and how much work an audit requires. The paper's target is research agents, but the doctrine transfers cleanly. A fluent output is not a governed artifact if its support cannot be reconstructed. A trace is not enough if it shows what happened without encoding why a claim was allowed. The source-of-truth candidate is the maintained surface that binds claims, evidence, constraints, and validation into a form that can be challenged.

This is where the evidence about AGENTS.md and agent README files must be handled carefully. Instruction files are a real signal. They show that teams are already creating machine-facing project artifacts that live beside source code and shape future runs. They also expose the failure mode. More context is not automatically more control. A long file can become stale, contradictory, overbroad, or ignored. Its value depends on task risk, metric, placement, maintainability, and whether any part of the document is connected to enforcement or evaluation. Context files are evidence for the emergence of specification surfaces. They are not proof that every repository-level instruction file is beneficial.

That caveat saves the argument from its most tempting overclaim. The future is not a world where every sentence in a repo becomes executable law. Software work has always had prose around it: tickets, comments, design docs, READMEs, runbooks, release notes, and Slack decisions. Most of it remains explanatory. Some of it is stale the day after it is written. The new thing is narrower and more consequential. Certain written surfaces now sit close enough to model execution, harness interpretation, validation, testing, trace review, and policy enforcement that they begin to govern behavior directly. They are still human-facing, but they are no longer merely human-facing.

The operational test is simple. If a file can change what an agent is allowed to do, what state it must preserve, what outputs count as valid, what trace violations matter, what tests are generated, what tools are reachable, or what claims can be carried forward, then it is part of the specification surface. If it merely explains the project without entering any control or review path, it is documentation. Documentation can be valuable. It can be beautiful. It can help a human understand the system. But it should not be confused with the artifact that governs an AI-assisted workflow.

This also clarifies the place of generated code. The code remains the executable material reality of the system. It is where performance, security, maintainability, and failure show up. But in AI-native work, the generated code is often the most visible downstream artifact rather than the most stable upstream one. A team that treats the generated diff as the whole truth will keep reviewing symptoms. A team that treats the specification surface as the source-of-truth candidate can ask a stronger set of questions: Was the intended behavior specified? Were the constraints checkable? Did the trace violate policy? Did the tests cover the risk? Did the generated implementation drift from the maintained surface, or did the maintained surface fail to say enough?

That is the professional doctrine hidden under the anti-vibe slogan. Vibe treats intent as atmosphere. A specification surface treats intent as infrastructure. It gives the team something to maintain when the model changes, something to inspect when an agent succeeds for the wrong reason, something to test when a prompt is edited, something to trace when a long-running workflow drifts, and something to argue over before the generated code becomes the only record of a decision.

The practical burden is less glamorous than the slogan. Teams need to decide which surfaces deserve authority. They need to keep those surfaces short enough to audit, structured enough to parse, and explicit enough to test. They need linting for instruction files, validators for workflow files, trace checks for multi-step runs, regression suites for prompt behavior, and claim ledgers when generated research or planning enters the system. They need to separate source surfaces from derived evidence: specification, implementation, test, trace, log, report. Each has a job. Confusing them makes the system harder to govern.

This is why "natural language is code" is the wrong frame. It is too broad to be true and too loose to be useful. The actual shift is more disciplined. Maintained specification surfaces are becoming source-of-truth artifacts where AI-assisted work needs reviewable intent, operational constraint, and repeatable validation. Some of those surfaces are written in ordinary language. Some are YAML. Some are markdown with machine-readable conventions. Some are tests, protocols, or trace-linked ledgers. Their common property is not syntax. Their common property is governance.

Once that becomes clear, the future of AI coding looks less like a prompt box and more like a repository of controlled surfaces. The prompt still matters, but it is no longer the whole interface. The model still matters, but it is no longer the only place where intelligence lives. The code still matters, but it may no longer be the only artifact worth calling source. The system becomes governable when the intent layer can be read before execution, checked during execution, and repaired after execution. That is the specification surface. That is where the new source of truth begins.

## Limits

This candidate does not claim that natural language is code, that generated implementation stops mattering, or that ordinary documentation is automatically a source-of-truth artifact. It also does not claim that more formal specification always improves model behavior. The argument depends on controlled, maintained, validated, typed, linted, trace-linked, or runtime-interpreted surfaces.

The non-agent software-engineering bridge papers listed in the package index are used here only as pressure and synthesis support. Direct quotation or close body reliance on `2602.00180`, `2603.24284`, `2512.14012`, `2512.14805`, `2508.06942`, or `2603.15691` should trigger targeted intake before promotion. Context-file claims must remain metric-specific and must keep the negative AGENTS.md caveat visible.
