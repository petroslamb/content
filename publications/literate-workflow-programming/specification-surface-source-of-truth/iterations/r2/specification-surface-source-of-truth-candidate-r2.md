# The Specification Surface Is the New Source of Truth

A code review can now fail before anyone reads the code. The generated diff is sitting in the pull request. The tests are green. The agent has written a confident summary of what changed. But the real question is harder to find: where is the durable statement of what this work was supposed to preserve? The ticket said "add export." The prompt lived in a chat. A design choice was settled halfway through a session and never made it back into the repository. By the time the reviewer arrives, the implementation is visible and the intent is atmospheric. The team is reviewing the downstream artifact because the upstream one was never made governable.

That is the quieter problem hiding under vibe coding. The risk is not merely that someone trusted a model too much. The deeper failure is that intent stays informal until generated code becomes the only object treated as real. Once that happens, every later question has to be reconstructed from symptoms. Why did the agent choose this schema? Which constraint was binding? What behavior was out of scope? Which test proves the important thing? Which instruction should survive the next model, the next run, or the next developer? If the answer lives only in a prompt transcript or a private mental model, the system has already lost part of its source of truth.

The object that repairs this is not "natural language." Loose prose is still loose prose. A README full of advice is not automatically a control plane. A one-off prompt in a chat window is not a maintained engineering artifact. The object that matters is a specification surface: a written surface that becomes operational because it is controlled, maintained, typed, linted, validated, trace-linked, interpreted by a runtime, compiled into tests, or used as the stable artifact against which generated behavior is checked. Its syntax is secondary. The decisive property is governance.

This is why the specification surface is larger than an agent-harness niche. Spec-driven development makes the broader software-engineering bridge explicit. Its premise is old but newly pressured by AI coding: code has often become the de facto truth because requirements drift, design documents rot, and the implementation is the only artifact everyone believes. Spec-driven development inverts that hierarchy by treating specifications as contracts that code implements, verifies, or derives from. It offers levels of rigor rather than one doctrine: spec-first when a specification guides initial implementation, spec-anchored when the specification and code stay aligned through tests or contracts, and spec-as-source when humans edit the specification and generated code is derivative.

That spectrum matters because it blocks the lazy version of the argument. The future is not every team throwing prose into a repository and calling it source. Spec-first work can still drift. Spec-anchored work needs tests, contract checks, and review habits that keep the surface alive. Spec-as-source only makes sense where generation tooling is mature enough and the domain can tolerate that discipline. The useful rule is enough specification to remove consequential ambiguity, with enough enforcement to make drift visible. Authority comes from the maintenance loop, not from the romance of writing things down.

The same point appears more sharply in "The Specification Gap." That paper studies a narrow but revealing failure mode: multiple code agents independently implement parts of the same class while the shared specification loses detail. When the specification is stripped from full docstrings down toward bare signatures, two-agent integration accuracy falls sharply, while a single-agent baseline degrades more gracefully. The important result is that weak specifications remove shared decisions the agents cannot reliably infer from their separate fragments.

The recovery result is even more useful for this essay. The paper's conflict detector can identify structural mismatches, especially when specifications are weakest, but conflict reports do not replace the missing shared specification in the studied recovery setting. Restoring the full specification is what recovers performance to the single-agent ceiling. Diagnosis explains the break. Specification repairs the coordination surface. That is a strong pressure test for the source-of-truth claim. When generated parts fail to integrate, the fix is not just better post-hoc inspection. The governing surface has to carry the decisions that independent work must share.

This makes the broader argument less metaphorical. A specification surface earns its value by letting a system coordinate, not by sounding formal. Human teams already know this through API contracts, BDD scenarios, acceptance criteria, architecture constraints, schemas, and interface definitions. Agents make the cost of weak surfaces more visible because they can generate plausible work faster than organizations can reconstruct intent. The specification gap is the machine-speed version of an old software problem: separate workers cannot reliably converge on unstated decisions.

The professional practice evidence points in the same direction. "Professional Software Developers Don't Vibe, They Control" studies experienced developers using coding agents through field observations and surveys. The headline is tempting, but the mechanism matters more than the slogan. Experienced developers use agents for speed while preserving agency over design and implementation. They plan before implementation, supervise outputs, validate changes, use version control, limit how much work an agent does at once, and rely on domain expertise to decide where agents are suitable. They do not treat agent output as autonomous authority.

That finding gives `vibe` its proper role in the essay. Vibe is a source-of-truth error, not a personality type. It asks the model to carry intent privately and then asks the generated code to stand as the public record. Professional control moves the burden back into artifacts: plans, specifications, tests, constraints, reviewable diffs, traces, and rollback points. The experienced developer's skepticism is infrastructural. Control has to live somewhere the team can inspect.

The strongest agent-specific papers then show how this surface becomes operational. In "Bootstrapping Coding Agents: The Specification Is the Program," the stable artifact is a compact specification that can generate an agent, which can then use the same specification to generate another implementation. The paper does not prove that prose should replace all code. It shows a controlled inversion: the specification is the durable object, and implementations become downstream products that can be compared against it. If they diverge, the repair target is the specification and its interpretation, not the mere fact that a file changed.

"Natural-Language Agent Harnesses" moves from product specification to execution structure. The harness contains decomposition, roles, state, adapters, contracts, verification, and durable artifacts in a form interpreted by a runtime. AgentSPEX pushes the same idea into a typed workflow language with steps, branches, loops, state management, checkpointing, tracing, replay, and verification. These are specification surfaces in a mature form. They are readable enough for people to inspect, structured enough for tools to parse, and operational enough to shape execution.

The important word remains surface. A surface can be read before execution, acted on during execution, and audited after execution. It has edges. It can be versioned, diffed, parsed, tested, and linked to evidence. A chat prompt vanishes into a session. A maintained workflow file can become part of the system's source. The distinction is not aesthetic. It determines whether the team can tell what changed, who authorized it, what constraints applied, and which failure should force the surface to be repaired.

ContextCov makes the transition from passive instruction to active invariant especially clear. Agent instruction files such as AGENTS.md, CLAUDE.md, or copilot-instructions.md can contain real project guidance, but guidance on the page is weak unless it enters a control loop. ContextCov extracts constraints into executable checks: shell shims, AST queries, architectural validators, and LLM-based judgments where deterministic checks are not enough. The document becomes a source of invariants. Failures reveal not only agent mistakes, but ambiguity, staleness, or drift in the instruction surface itself.

Test-Driven AI Agent Definition and FASTRIC make the same discipline visible at the prompt and interaction level. A natural-language product specification can generate visible and hidden tests, then drive prompt and tool refinement against those tests. A multi-turn prompt protocol can be specified enough to check roles, state transitions, tool use, and procedure. The point is not that stricter form always improves behavior. The point is that the right surface makes behavior inspectable. Formality is useful when it gives a team something to test and repair.

Trace and audit papers complete the downstream side of the hierarchy. AgentPex evaluates traces for procedural violations that outcome-only scoring can miss. AgentFixer uses validation checks, trace comparisons, root-cause analysis, and repair suggestions to turn failures into refinement pressure. "From Fluent to Verifiable" shows why polished outputs are not enough when claim-evidence relations cannot be reconstructed. These systems are not the source of truth by themselves. They are evidence surfaces. They tell the team whether execution respected the specification surface and where the surface failed to say enough.

That distinction is essential for context files. Agent READMEs and repository-level instruction files are real signals that software teams are creating machine-facing project artifacts beside source code. They also expose the trap. More context does not automatically produce more control. A long instruction file can be stale, contradictory, ignored, or useful only for a narrow class of tasks. The evidence supports a disciplined claim: context files can become part of a specification surface when they are maintained and connected to evaluation or enforcement. They remain documentation when they merely explain the project.

The operational test is simple. If a file can change what an agent is allowed to do, what state must persist, which tools are reachable, what outputs count as valid, what tests are generated, which trace violations matter, or what claims can be carried forward, then it belongs near the specification surface. If it only describes the project for human orientation, it may be valuable documentation, but it should not be confused with the artifact that governs AI-assisted work.

This also clarifies the place of generated code. The code is still the executable material of the system. It carries bugs, latency, security exposure, maintenance cost, and user consequences. A serious team still reviews it. But in AI-assisted work, the generated implementation is often the most visible downstream artifact, not the most stable upstream one. A team that treats the diff as the whole truth keeps reviewing symptoms. A team with a maintained specification surface can ask the stronger questions: Was the intended behavior specified? Were the constraints checkable? Did the implementation drift from the surface, or did the surface fail to carry the needed decision?

The practical burden is plain. Teams need to decide which surfaces deserve authority. They need to keep those surfaces short enough to audit, structured enough to parse, explicit enough to test, and close enough to execution that violations hurt. They need linting for instruction files, validators for workflow files, regression suites for prompt behavior, trace checks for multi-step runs, contract tests for generated interfaces, and claim ledgers when generated research or planning enters the system. This is where control lives when implementation can be generated faster than intent can be rediscovered.

The wrong frame is "natural language is code." That frame is too broad and too careless. Some specification surfaces are written in ordinary language. Some are YAML. Some are markdown with machine-readable conventions. Some are tests, schemas, protocols, trace policies, or claim-evidence ledgers. Their common property is governed authority: they are maintained surfaces that systems read, tools check, humans review, and failures push back into revision.

Once that becomes clear, AI coding looks less like a prompt box and more like a repository of controlled surfaces. The prompt still matters, but it cannot be the only place where intent lives. The model still matters, but it cannot be the only place where judgment hides. The code still matters, but it cannot be the only artifact worth governing. The system becomes controllable when intent can be read before execution, checked during execution, and repaired after execution. That is the specification surface. That is where the new source of truth begins.

## Limits

This candidate does not claim that natural language is code, that generated implementation stops mattering, that every document is a source-of-truth artifact, or that more formal specification always improves model behavior. It also does not claim that every team should adopt spec-as-source. The argument depends on controlled, maintained, validated, typed, linted, trace-linked, or runtime-interpreted surfaces that actually enter a control, review, or validation loop.

The bridge papers support a narrowed public claim. `2602.00180` supports specification authority as a software-practice spectrum, not universal spec-as-source adoption. `2603.24284` supports specification-first coordination under the studied multi-agent code-generation conditions, not a guarantee that full specifications eliminate every coordination cost. `2512.14012` supports professional-control practice among experienced developers, not a claim that every developer already works this way.
