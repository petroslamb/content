# Publication Strategy And Archive

This directory is the publication operations layer for Rooted Layers.

It holds five different things:

- the raw downloaded Substack archive
- the curated mapping between published essays and repo folders
- the tracked migration manifest for repo-link rewrites
- the 11ty GitHub Pages mirror
- the editorial atlas for publication-object analysis
- longer-term publication strategy notes

Substack remains the canonical publication surface. The mirror exists to keep public essays close to their research folders, raw snapshots, and provenance.

## Directory Map

- [`substack_archive/`](substack_archive/): generated fetch cache with normalized markdown, HTML snapshots, localized assets, and `metadata.json`
- [`post_map.yaml`](post_map.yaml): hand-edited mapping from Substack slug to research folder, series metadata, tags, and summary text
- [`link_migration_manifest.yaml`](link_migration_manifest.yaml): tracked map of package moves plus repo-link and Substack-link rewrites for the `publications/` migration
- [`mirror/`](mirror/): 11ty source for the public GitHub Pages mirror
- [`editorial_atlas/`](editorial_atlas/): canonical atlas data, docs, and pull-sheet artifacts for the essay corpus
- [`future_publication_strategy.md`](future_publication_strategy.md): longer-term planning notes
- [`publication_analysis_results.md`](publication_analysis_results.md): qualitative review material

## Operating Model

The working split is intentional:

- `substack_archive/` is generated data. Do not hand-edit archived post files there.
- `post_map.yaml` is curated data. Edit this file when you want to connect an essay to a research folder, add a series, change a summary, or adjust tags.
- `link_migration_manifest.yaml` is the tracked planning layer for package moves and later live Substack link patches.
- `editorial_atlas/` is curated strategy data. Edit it when you want to change the atlas scores, pulls, or analysis docs.
- `mirror/` is presentation code. Edit it when you want to change the public site.

Inside `editorial_atlas/`, the editable rubric sources are the
model-specific `rubric_assessments_*.yaml` files. The published
machine-readable view `atlas_data.json` is generated from the complete rubric
sources and should not drift from them.

## Commands

Run these from the repository root:

```bash
npm run sync:substack
npm run sync:editorial-atlas
npm run build:mirror
npm run dev:mirror
npm run check:mirror
```

What each command does:

- `sync:substack`: pulls the public publication feed, refreshes local markdown and HTML snapshots, localizes assets, updates `metadata.json`, and regenerates the root README mapping table
- `sync:editorial-atlas`: regenerates `editorial_atlas/atlas_data.json` from complete `editorial_atlas/rubric_assessments_*.yaml` files
- `build:mirror`: builds the 11ty site into `publication_strategy_and_archive/mirror/_site`
- `dev:mirror`: runs the 11ty dev server for mirror work
- `check:mirror`: rebuilds the site and validates metadata, rubric-derived atlas generation, local assets, generated README content, and built internal links

## Data Files

### Generated Manifest

[`metadata.json`](substack_archive/metadata.json) is generated by the sync script and acts as the machine-readable archive manifest.

Each post entry includes:

- `slug`
- `title`
- `url`
- `post_date`
- `audience`
- `fetched_at`
- `content_hash`
- `md_path`
- `html_path`
- `hero_image`
- `mirror_enabled`

### Curated Map

[`post_map.yaml`](post_map.yaml) is the hand-maintained metadata layer used by both the mirror and the generated publication mapping table in the root README.

Common fields:

- `research_folder`
- `series_key`
- `series_title`
- `series_order`
- `summary`
- `tags`
- `featured`
- `status`

## Automation

Two GitHub Actions back this system:

- [`sync-substack-archive.yml`](../.github/workflows/sync-substack-archive.yml): scheduled or manual archive sync that opens a pull request when public posts change
- [`deploy-mirror.yml`](../.github/workflows/deploy-mirror.yml): GitHub Pages deployment workflow for the mirror

The public mirror is published at [https://petroslamb.github.io/content/](https://petroslamb.github.io/content/).

## Recommended Workflow

1. Run `npm run sync:substack`.
2. Review `post_map.yaml` for any newly discovered slugs.
3. Run `npm run check:mirror`.
4. Commit and push to `main`.
5. Let the deploy workflow publish the mirror.

## Manual Import Fallback

Use this when the Substack sync workflow is blocked by upstream `403` responses but you already have the final markdown and local image assets.

The manual import target is still the tracked archive under [`substack_archive/`](substack_archive/). The mirror reads from the archive manifest and local snapshot files, so a manual import can publish new posts without changing the mirror code.

Minimum required artifacts per post:

- one markdown snapshot in `publication_strategy_and_archive/substack_archive/`
- one HTML snapshot in `publication_strategy_and_archive/substack_archive/`
- any referenced local images copied into `publication_strategy_and_archive/substack_archive/assets/`
- one matching entry in [`metadata.json`](substack_archive/metadata.json)

Recommended manual process:

1. Start from the canonical Substack slug, title, URL, and publish timestamp.
2. Copy the markdown into `substack_archive/` using the standard filename pattern: `YYYY-MM-DD_<slug>.md`.
3. Rewrite any relative image links so they point to `assets/<filename>`.
4. Copy the actual image files into `substack_archive/assets/`.
5. Create a same-stem HTML snapshot beside the markdown file.
6. Add a `metadata.json` entry with the same slug and paths, `audience: "everyone"`, and `mirror_enabled: true`.
7. Run `npm run check:mirror`.
8. Commit and push to `main` so the Pages deploy workflow republishes the mirror.

Required `metadata.json` keys:

- `slug`
- `title`
- `url`
- `post_date`
- `audience`
- `fetched_at`
- `content_hash`
- `md_path`
- `html_path`
- `hero_image`
- `mirror_enabled`

Replacement behavior:

- Manual imports should use the canonical Substack slug.
- If automated sync starts working again later, the sync is expected to replace the manual snapshot for that same slug rather than create a second visible post.
- In other words, manual import is a fallback publication path, not a second archive namespace.

## Notes

- The mirror only publishes posts where Substack reports `audience == "everyone"`.
- Series in the mirror are currently defined in `post_map.yaml`, not imported automatically from Substack sections.
- Built output in `mirror/_site` is not committed.
