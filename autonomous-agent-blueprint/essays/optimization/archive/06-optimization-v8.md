# Operating Agents Bonus: The Workflow Is the Object

A document-classification workflow had been in production for three months. It was not perfect, but it was useful. A human corrected the tail of the work, and the economics still made sense. Then the team decided to improve it.

Over the next six weeks they edited the system prompt repeatedly. Some edits seemed to help the recent failures they were staring at. Later edits quietly regressed other cases. The prompt grew longer. Tool descriptions changed. Nothing about the underlying evidence improved because there was no stable evaluation set, no clean record of which failure types mattered most, and no agreement about whether latency and correction rate belonged inside the objective or merely counted as unpleasant side effects.

That is the flattering mistake that makes optimization feel productive when it is not. Teams call prompt churn optimization because the prompt is the surface they can see and edit quickly. The stricter default is less flattering and more useful. Optimization begins with measurement, not edits. The unit of improvement is the workflow, not the prompt. The first question is not what wording should we try next. It is which layer is failing often enough to deserve intervention.

Once a system exists, the instinct to optimize locally becomes very strong. A bad output appears, and the fastest response is to change the prompt. Sometimes that works. Just as often it misdiagnoses the layer. An agent workflow usually has several improvement surfaces at once: output schemas, tool descriptions, retrieval configuration, workflow decomposition, prompts, and feedback loops. Any one of them can be the true source of visible failure. A malformed output can look like a reasoning issue when it is actually a schema issue. A weak answer can look like a prompt issue when retrieval brought in the wrong evidence. A brittle workflow can look like a model issue when the steps are in the wrong order. If the diagnosis starts and ends with prompt wording, the surrounding architecture disappears from view just when it should become the object of scrutiny.

That is why *OPRO* matters conceptually. The paper treats prompt optimization as a measured search problem over examples rather than as artisanal tinkering. The important word there is examples. Without a fixed evaluation set, there is no stable signal against which a candidate change can be judged. *TextGrad* extends the same lesson by treating the textual workflow itself as an object that can receive feedback, not just the final prompt. Neither paper is most valuable here as a recipe to imitate directly. Their deeper value is that they make the prerequisite visible. Without a stable objective and a repeated evaluation loop, there is no meaningful optimization. There is only editing under recency bias.

That is why the order of improvement has to be more conservative than most teams want. The first move is to lock an evaluation set. If you do not have a fixed set of representative cases with known good outcomes, you do not yet have optimization. You have taste and anecdotes. The second move is usually to inspect schemas and contracts. A surprising amount of system pain comes from outputs that downstream components cannot consume reliably. Clean schemas often remove whole classes of failure more cheaply than any prompt rewrite. The third move is to inspect retrieval and evidence quality. If the workflow reasons over weak, partial, or irrelevant evidence, prompt edits are often compensating for missing context rather than correcting the real problem. Only after those layers are sufficiently clean does it make sense to tune prompts and tool descriptions against the evaluation set. Only after that does it make sense to revisit workflow topology. Self-improvement loops and topology search belong later still, once the object of measurement is stable enough that a change can be interpreted without self-deception.

The discipline here is not anti-optimization. It is anti-premature optimization theater. The field likes to discuss the exciting end of the subject: prompt search, graph search, self-improving systems, workflows that rewrite themselves. Production teams usually need a duller first move. They need to freeze the object of argument. A system with a stable eval set, known-good outcomes, regression guards, and owner-visible metrics can finally turn a prompt edit from a vibes discussion into a testable intervention. Without that structure, the last ugly incident gets more influence than the fifty cases that quietly stayed stable or quietly got worse.

This is also why measurement is not overhead. A real evaluation layer is part of the system. It has defined inputs, defined outputs, owners, stored comparisons over time, and regression conditions that can stop a bad change from being celebrated as progress. It records accuracy, latency, cost, retries, approval rates, and human correction rates against representative tasks. It tells the team whether the system is improving in the dimensions that matter rather than in the dimensions that happen to be visible on a given afternoon. This is where LLM-as-judge work becomes useful, though only with discipline. *MT-Bench* and related work matter less because automated judges are magically trustworthy and more because they show how comparative evaluation can become operational enough to support real workflows. A judge that has not been calibrated against human labels on a relevant sample is not a measurement instrument yet. It is a guess generator with a dashboard.

The wider optimization literature belongs in the story as well, but it belongs later. *AFLOW* and *GPTSwarm* matter because they make workflow structure itself searchable. *Reflexion* and *Voyager* matter because they show lighter ways a system can improve from failure and success traces over time. The builder lesson across that cluster is not excitement first. It is scope and sequence. Feedback loops are useful when the system is already stable enough to trust the signal that feeds them. A reviewed correction can become a better prompt, a tighter procedure, or a reusable routine. A workflow that is still unstable at the schema, retrieval, or topology level should not be given permission to rewrite itself broadly. It will optimize around noise, entrench the wrong local behavior, and mistake drift for improvement because the objective itself is still muddy.

That is the real value of bounded self-improvement. Improve only the surfaces you can validate. Promote only the routines that have earned promotion. Search topology only after the simpler explanations for failure have been ruled out. In a mature system, self-improvement should feel less like science fiction and more like controlled maintenance. The system becomes better not because it is theatrically rewriting itself, but because the workflow has accumulated enough measurement discipline that reviewed improvements can be admitted without corrupting the baseline.

A live system has something a prototype does not have: operational evidence. It has real latency distributions, not guesses. It has correction logs, not memories of the worst recent incident. It has evidence about which task classes break most often, which tools are rarely useful, which approval gates fire constantly, and which retrieval patterns return noise. That is where the optimization signal lives. The team in the opening example already had that evidence. They simply were not using it. If they had built an evaluation set from human corrections, separated the failures by type, and inspected the distribution before editing, they likely would have discovered that one document class with underspecified metadata accounted for most of the pain. A schema and retrieval fix would have helped far more than another week of prompt rewrites.

That is why optimization belongs at the end of this series. It depends on the earlier layers being real enough to observe. Before that point, optimization is often just a more flattering word for experimentation. The workflow becomes the object only once the system is legible enough to tell you where it hurts.

## Selected Sources

[OPRO](https://arxiv.org/abs/2309.03409) matters because it makes the prerequisite for optimization explicit. No stable objective, no real optimization.

[TextGrad](https://arxiv.org/abs/2406.07496) matters because it broadens the unit of optimization from one prompt to a larger textual workflow and therefore reinforces the chapter's main claim.

[AFLOW](https://arxiv.org/abs/2410.10762) and [GPTSwarm](https://arxiv.org/abs/2402.16823) matter because they push optimization up from local components to workflow structure itself. They are useful precisely because they sharpen the need for restraint.

[Reflexion](https://arxiv.org/abs/2303.11366) matters because it shows how reviewed failure can become reusable signal instead of staying trapped as a dead log.

[Voyager](https://arxiv.org/abs/2305.16291) matters because it frames self-improvement through validated routine accumulation rather than unrestricted self-mutation.

[Judging LLM-as-a-Judge with MT-Bench and Chatbot Arena](https://arxiv.org/abs/2306.05685) matters because it clarifies both the usefulness and the calibration burden of model-based evaluation once a workflow is serious enough to need it.
