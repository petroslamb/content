# Operating Agents I: When Language Becomes Accountable

A procurement team spent months building a language system that looked, in every meeting, like an agent. It could read vendor policies, explain approval logic, draft the purchase-order payload, and tell an operator exactly what should happen next. Stakeholders loved the demos because the system sounded operational. It named the right fields, the right exceptions, and the right downstream systems. It sounded like a machine that knew how to get work done.

Nothing happened until a human translated that prose into clicks and API calls.

So the team gave the system write access to the procurement service. The first run failed for a reason that looked almost trivial. The model filled `currency_code` with `USD dollars` instead of `USD`, and the schema rejected the write. The second failure was worse because it looked cleaner. The workflow reached the correct endpoint and appeared to succeed, but the downstream service had changed how it reported deferred writes. The agent treated a partial acknowledgment as completion and moved on. The purchase order never landed. Two weeks later a supplier called asking where it was.

That sequence contains the boundary this chapter is about. Natural-language plans are often mistaken for agency because they sound operational. They are not operational. They are advice. Agency begins at the point where a system can change state outside the prompt and be held accountable for the result. Once that boundary is crossed, the design problem changes with it. The important questions stop being mostly about eloquence, and even mostly about reasoning in the abstract. They become questions about interfaces. What surface can the system touch. How are arguments validated. What comes back after the action. What permissions govern the call. How would you replay the event. How would you know the action failed. Those are system-design questions, not prompt-design questions.

That is why action belongs at the front of the series. It is the first place where agent rhetoric becomes expensive. A stronger model attached to vague action boundaries will fail in ways that are hard to localize, because the system never decided where interpretation should stop and contract should begin. A more modest model attached to typed, observable, permissioned actions can often be debugged, corrected, and improved. In production, action representation usually matters more than raw model capability.

There is a flattering definition of agency that hides this shift. It says an agent is a system with reasoning, memory, planning, and tool use. By that standard, an elaborate assistant already looks agentic. The production definition is harsher and more useful. An agent is a workflow that can take a bounded action against an external surface, observe the result, and continue from what actually happened. If the system only describes what should happen and a human silently performs the workflow, the human is still the action layer. This is why the step from assistant to agent often feels small in a demo and large in engineering. The demo only has to make intent sound plausible. The real system has to survive schema validation, permission scopes, retries, partial failures, stale outputs, and ambiguous acknowledgments.

The literature on tool use became practically useful when it stopped treating tool use as one capability and started making the seams visible. Production systems do not fail at action in the abstract. They fail at recognizable interfaces between subtasks. Sometimes the workflow stays in prose too long and answers from plausibility when it should have reached for live state. Sometimes it chooses the wrong interface among several similar ones. Sometimes it chooses the right interface and fills one field incorrectly. Sometimes the execution surface is too broad for the authority the step deserves. Just as often, the write is fine and the interpretation is wrong. A queued job is treated as a completed one. A warning is treated as success. A raw environment message becomes control policy by accident. If those seams are not explicit, every miss gets dumped into the vague bucket called model behavior.

That is why the narrowest useful action surface is usually the best one. If a clean API exists, use it. APIs give you schemas, scoped permissions, replayable calls, and inspectable logs. If the work is software or data transformation, code execution is often the right action surface because code can be tested, sandboxed, and reviewed before side effects occur. If the work lives mainly in structured enterprise data, SQL or a typed query layer is often the real operating surface even though agent discourse tends to underrate it. Browser automation becomes necessary when the system of record exposes no cleaner path. GUI action is the fallback after that. The hierarchy is not about elegance. It is about how much ambiguity the interface introduces. Every step downward trades machine-readable structure for interpretive burden, and interpretive burden is where fragile automation begins to pretend it is intelligence.

Once you see action that way, the observation side of the loop becomes impossible to ignore. Many teams define what the model can send and barely define what the model is allowed to conclude from what comes back. That omission is expensive. If tool results arrive as raw HTML, raw logs, or broad success language, the model has to infer too much. It may infer correctly often enough to look competent, which is exactly why the weakness survives. The strongest action systems therefore treat the observation contract as seriously as the invocation contract. Success has to mean something machine-legible. Partial success has to mean something machine-legible. A state that requires retry, review, or escalation has to be explicit in the returned object rather than reconstructed later from polite text.

This is one reason papers such as *Toolformer*, *Gorilla*, and *SWE-agent* mattered. They helped move the argument away from whether a model can call a tool in principle and toward the colder question of what kind of boundary lets a system fail in ways a builder can still diagnose. *Toolformer* normalized structured tool use as part of competence rather than an exotic wrapper around language generation. *Gorilla* made interface discrimination and argument construction legible as distinct bottlenecks. *SWE-agent* showed, in an unusually inspectable setting, what happens when actions and results become replayable enough that failure can be made local.

The conservative default follows directly from that history. Start with a narrow action layer over typed APIs, code, search, or queries. Validate arguments before execution. Return typed observations after execution. Instrument the major seams separately so that a miss can be located instead of narrated. Broaden the surface only when the environment forces you to. Add browser control when the system that matters has no usable API. Add GUI control only when more structured surfaces are unavailable. Add more tools only when the current boundary genuinely blocks necessary work, not because broader capability looks like maturity.

A convincing plan is not agency. Agency begins where the system can change state and be judged on the result. That is why the first serious agent decision is not about how smart the model seems. It is about how narrow and accountable the action boundary can remain once language stops describing the workflow and starts participating in it.

## Selected Sources

[Toolformer](https://arxiv.org/abs/2302.04761) matters here because it normalized the idea that useful work often begins when language chooses an external interface instead of continuing to answer from plausibility.

[Gorilla](https://arxiv.org/abs/2305.15334) matters because it narrowed tool use down to interface selection and argument construction. That is exactly where many production failures live.

[SWE-agent](https://arxiv.org/abs/2405.15793) matters because it shows what a replayable action surface looks like once the environment returns machine-checkable feedback. It makes the argument for narrow, inspectable action loops unusually concrete.

[BIRD](https://arxiv.org/abs/2305.03111) and [Spider 2.0](https://arxiv.org/abs/2411.07763) matter because they help frame structured data work as a first-class action surface rather than a side topic. Much enterprise action is really argument construction against constrained schemas.

[A Real-World WebAgent](https://arxiv.org/abs/2307.12856) and [OmniParser](https://arxiv.org/abs/2408.00203) matter as escalation references. They show what happens when cleaner interfaces run out and the workflow has to tolerate a weaker action contract in order to reach the system that matters.
