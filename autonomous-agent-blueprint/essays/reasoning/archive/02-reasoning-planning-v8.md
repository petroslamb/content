# Operating Agents III: The Lightest Correct Scaffold

A claims-processing workflow built with a strong base model and a careful prompt had a task that looked contained: read the claim, check the criteria, return a structured recommendation. In production it rarely said anything absurd. It simply skipped one dependency, collapsed several checks into one fluent answer, or treated one missing fact as though it were present. The output looked polished enough to pass a casual read and brittle enough to fail the moment a reviewer checked the file.

The team reacted the way many teams react. They added prompt detail. They tried more context. They discussed a stronger model. None of that touched the real problem because the real problem was not mainly the model's intelligence. The workflow was asking one generation to do the work of several. A decomposition pass and a verification step cut the obvious misses quickly. What remained was narrower and more useful. Cases tied to live payer status still failed because the workflow was reasoning from stale state rather than forcing a fresh check against the external ledger. The first fix helped, but it also exposed the next failure shape. The system had never had one reasoning problem. It had several scaffold problems sitting on top of each other.

That sequence is the key to the chapter. Many production reasoning failures are scaffold failures before they are intelligence failures.

The easiest way to waste time in agent design is to answer the wrong failure with a more impressive method. A workflow skips a dependency, so the team reaches for search. It hallucinates on live state, so they add critique. It produces unstable answers, so they stretch the prompt and call it planning. The result is usually not more intelligence. It is more machinery wrapped around a diagnosis error. The practical question is colder than that. What exact failure shape exists here, and what is the lightest scaffold that corrects it. If the system keeps compressing dependent checks into one answer, the first fix is decomposition. If it keeps reasoning as though the environment will obediently match its expectations, the first fix is a reason-act-observe loop. If a plausible answer is becoming consequence before it has earned trust, the first fix is verification. If the workflow keeps failing because sequence itself carries the risk, the plan may need to become a first-class object. Only when those simpler layers are already working and the task still contains genuine branching difficulty does search begin to earn its cost.

That is why *Least-to-Most Prompting* still matters. The paper solved a problem builders continue to underrate. Many tasks arrive wrapped as one judgment even though they are structurally several judgments with dependencies. Eligibility before exception. Evidence before synthesis. Current state before recommendation. The durable contribution of the paper was not a clever way to make reasoning look longer. It was a clearer way to externalize the sequence of subproblems before the model tried to improvise the whole thing at once. Once those dependencies are visible, the workflow stops pretending that a multi-stage problem is a one-stage act of eloquence. Decomposition is often the least glamorous repair in the stack and one of the most valuable. It makes hidden logic visible enough to inspect.

The same logic explains why *ReAct* remains a default rather than a decorative option. The moment the task depends on tools, live records, code, or environment state, reasoning has to stop being a monologue and become a control loop. Chain-of-thought prompting had already shown that models could narrate reasoning. What it could not do was keep that reasoning answerable to a world that could contradict it. *ReAct* bound thought to action and observation so the next step had to proceed from what actually happened rather than from what the model expected to happen. That distinction still explains a large share of production failure. A workflow that keeps reasoning in prose while the real state lives in a ledger, a browser, a database, or a tool result is not mainly underpowered. It is disconnected from reality.

Verification belongs in the same family of corrections. Many workflows do not merely need better answers. They need answers that deserve consequence. *Chain-of-Verification* mattered because it took a vague norm and gave it a place in the workflow. Draft the answer. Generate the questions that would challenge it. Answer those separately. Revise only after the checking stage. The significance of that move is structural. It stops the first generation from silently certifying itself. A coherent answer may still be wrong. A polished recommendation may still be unsupported. Verification creates a stage where trust has to be earned rather than merely implied by fluency. This is one of the places where teams most often misread a workflow failure as a model failure. The problem is not always that the draft was too weak. Just as often, the draft was allowed to become consequential before anybody asked it hard questions.

Planning enters only after those simpler corrections are in place. Reasoning and planning are adjacent, but they are not interchangeable. A system can reason entirely inside language. Planning becomes a different engineering job when the order of operations, the use of resources, and the commitment points inside the workflow become part of the risk. That is where work such as *LLM+P* becomes useful. Its value is not that every hard task wants a formal planner. Its value is that it marks the point where prose can no longer carry the constraints safely. If prerequisites stay implicit, commitment points arrive too early, or hard constraints remain buried in narrative reasoning, the sequence itself has become the risk. That is the moment planning begins.

Search belongs later still. Methods such as *Tree of Thoughts* and later search-heavy planner families matter because some tasks really do branch. They have several plausible paths, real dead ends, and choices that simpler scaffolds cannot resolve cleanly. What search does not fix is weak decomposition, missing observation, or absent verification. If those layers are still weak, search mostly magnifies confusion and latency at the same time. That is why the escalation rule has to stay severe. Decompose first. Ground the workflow in live state. Verify before consequence. Promote the plan when sequence itself is the risk. Only after that should search enter the picture, and only if branching difficulty still remains after the simpler structure has been installed.

The practical default that follows is narrower than much of the field likes. Decompose multi-part work into explicit subproblems. Use a reason-act-observe loop whenever the world matters. Verify consequential claims before they become actions. Promote the plan into a first-class object only when the order of operations itself is the source of risk. Treat search as a late escalation for tasks that genuinely branch. If one generation is doing the work of several, a better model usually buys a more polished mistake rather than a sounder system.

That is why the chapter's claim is best stated as a rule of diagnosis. If your agent reasons badly, do not start by blaming the model. Start by asking what scaffold the task actually requires, and whether the workflow has installed it yet.

## Selected Sources

[Least-to-Most Prompting](https://arxiv.org/abs/2205.10625) matters because it formalizes decomposition as an architectural intervention rather than a cosmetic prompt trick.

[ReAct](https://arxiv.org/abs/2210.03629) matters because it binds reasoning to action and observation, which is why it remains the clearest default for workflows that depend on live state.

[Chain-of-Verification](https://arxiv.org/abs/2309.11495) matters because it gives verification a real place in the workflow instead of leaving it as a vague aspiration.

[LLM+P](https://arxiv.org/abs/2304.11477) matters because it marks the escalation boundary where sequence itself becomes risky enough that prose is no longer a sufficient planning substrate.

[Tree of Thoughts](https://arxiv.org/abs/2305.10601) matters because it clarifies what genuine branching search is for, and therefore also clarifies what kinds of failures should not be answered with search.
