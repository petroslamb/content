# Operating Agents I: When the Model Starts Doing Things

The difference between an assistant and an agent does not begin when the model sounds more decisive. It begins when language stops being commentary on the task and starts becoming accountable state change. A system that drafts an email remains a language system until someone or something else decides whether the draft will be sent, to whom, with what parameters, against what state, and under what authority. A system that can actually send the message has crossed into a different engineering category. The same is true for database updates, code edits, browser submissions, purchase flows, tickets, and file writes. The moment the system can do rather than merely describe, the design problem changes from answer quality to action architecture.

That shift matters because the practical challenge is not only whether the model can pick a tool. The challenge is whether the entire action path is inspectable. Which surface is the system acting on? How are those actions represented? What counts as a successful observation after execution? What permissions are attached to the action? How does the workflow recover when the environment returns something partial, stale, or ambiguous? The blueprint is right to treat these questions as central because they define whether action remains governable after the first happy-path demo stops helping.

The literature on tool use and action systems makes a point that public agent writing often softens: action surfaces are not interchangeable. An API call, a SQL query, a shell command, a browser submission, and a GUI click may all look like "tool use" from a distance, but they imply different observability, replayability, and failure costs. The narrowest surface that still reaches the work is usually the best one because it minimizes both ambiguity and blast radius. Typed APIs are stronger than browser interaction when they exist. SQL is stronger than scraping when the task is genuinely structured-data work. Code is stronger than free-form narration when the workflow needs execution, tests, and replayability. Browser action is a real tool, but it is usually an escalation. GUI action is real too, but it is a last resort rather than a maturity badge.

This is where the action chapter is more important than the usual agent rhetoric suggests. It explains that the real transition from assistant to agent is not psychological. It is representational. The chapter's action ladder, echoed by the strongest papers in the cluster, moves from plain text to code to typed invocations in real environments. That ladder matters because plain text is the weakest action representation. It can describe an intended step, but it cannot execute, replay, or verify it with the same discipline that code or typed calls can. Once a system can express its next step as a SQL query, a tool schema, a command, a patch, or a constrained browser action, the workflow becomes more than eloquent. It becomes testable.

Toolformer normalized the idea that calling tools can be part of the model's operating pattern rather than a bolted-on afterthought, and Gorilla made the point more concrete by showing how much of practical tool use is really about choosing the right API and filling the right arguments accurately rather than gesturing at capability in general terms. HuggingGPT then widened the frame by treating the model as a controller over specialized capabilities rather than a monolith that should solve every part of the task itself. The deeper lesson across those papers is not that every agent should become a general controller. The lesson is that action design is already an architecture problem before the first real execution happens. The agent needs a narrow surface, a clean schema, a bounded authority set, and a way to turn raw execution results back into useful observations (Schick et al.; Patil et al.; Shen et al.).

That last point is where many systems fail quietly. Teams pay attention to the outbound action and neglect the return path. They log the fact that an API was called but not the semantics of the response. They record that a button was clicked but not the post-click state that matters. They capture an exception string but not the machine-readable category that would let the workflow recover intelligently. The blueprint is right to insist that the observation contract is half the action layer. An action without a clear observation is only a narrated guess about what the world will look like next. Strong agent systems do not just act. They make the environment legible enough for the next reasoning step to operate on evidence instead of wishful interpretation.

This is also why action systems need recovery logic that is richer than apology. If a tool partially succeeds, the workflow has to know whether partial state is safe, reversible, or escalatable. If a schema mismatch occurs, the system has to know whether the problem is recoverable through correction, retry, or handoff. If a browser session reaches a new state, the workflow has to know whether it is still on the intended path. These are not cosmetic concerns. They are the operational seams where a prototype becomes an auditable system or collapses into expensive ambiguity. The best action papers keep returning to this point from different angles. Mind2Web and related web-agent work show how brittle action becomes when the environment is broad and variable. SWE-agent shows the opposite lesson from a more structured domain: when the environment is built around executable artifacts, tests, and file operations, the agent's action loop becomes more inspectable and therefore more improvable (Deng et al.; Yang et al.).

The database and analytics side of the chapter makes the same point in a less theatrical domain. BIRD and Spider 2.0 matter because they show that one of the most valuable practical action surfaces is not a humanoid interface at all. It is structured data access. A large amount of enterprise work is not about browsing or clicking. It is about querying, filtering, reconciling, aggregating, and transforming data under clear schema constraints. That work is often a better fit for typed SQL action than for screen-based control because the representation itself is already formal enough to inspect and verify. The agent question is therefore not whether the model can operate a computer. The question is whether the environment gives the system a stronger surface than the computer-use fallback, and whether the team is disciplined enough to use it (Li et al.; Lei et al.).

The explanatory point the blueprint leaves mostly implicit is that action surfaces are not only technical choices. They are governance choices. The moment a workflow chooses browser action over API action, or GUI action over code, it is not just changing implementation style. It is changing how errors will be localized, how permissions will be scoped, how replay will work, and how postmortems will be written. That is why "computer use" is such an unstable public metaphor. It bundles many radically different forms of action under one thrilling label. The more serious engineering stance is stricter. Pick the narrowest surface that still reaches the task. Represent actions in the strongest form the environment allows. Separate planning authority from execution authority when the stakes justify it. Normalize outputs into typed observations before they flow back into reasoning. Treat retries, partial success, and rollback as part of the action architecture rather than as emergency patches.

Once those rules are clear, the practical doctrine of the chapter becomes simple. Start with typed APIs where possible. Use SQL or other structured interfaces when the task is fundamentally data-centric. Use executable code when the work needs replayability, tests, or deterministic transformation. Move to browser action only when the system of record really lives in the browser. Use GUI action only when legacy constraints leave no cleaner surface. This is not a law of nature. It is a bias toward inspectability. And inspectability is what keeps action from becoming theatrical autonomy.

## Resources And References

### [Builder Blueprint: Action Systems and Tool Use](https://github.com/petroslamb/content/blob/main/autonomous-agent-blueprint/practical-chapter-blueprints/03-action-tool-use-blueprint.md)

This blueprint matters because it translates the essay's argument about action surfaces, representation strength, and observation contracts into concrete defaults, escalation rules, and anti-patterns.

### [Toolformer](https://arxiv.org/abs/2302.04761) (2023)

Toolformer matters because it changes the conceptual burden of proof. Before papers like this, tool use could still be treated as an external wrapper around a language model. After it, that position becomes harder to defend. The paper shows that the model can be taught to call tools as part of its normal operating behavior, which means the design conversation has to move from "should we use tools at all?" to "what kind of tool interface produces reliable action?" That shift is one reason the action chapter belongs so early in a practical reading order.

Its limitation is equally important. Toolformer does not solve workflow design by itself. It does not decide which tool catalog is safe, what counts as a valid observation after execution, or how rollback should work when the environment changes under the model. The right way to use Toolformer is therefore not as a production recipe but as the paper that made tool invocation architecturally normal (Schick et al.).

### [Gorilla](https://arxiv.org/abs/2305.15334) (2023)

Gorilla matters because it treats tool use as an argument-construction problem rather than a vague intelligence problem. Many action failures do not come from the model lacking a general notion of what should happen. They come from the model choosing the wrong function, filling the wrong field, or misunderstanding the semantics of an API. Gorilla makes that failure mode legible. It turns attention toward schemas, retrieval over tool descriptions, and exact invocation rather than toward generalized agent mystique (Patil et al.).

It is also a useful corrective to the overbroad way many teams talk about tool use. A workflow that merely knows a tool exists is not yet action-capable in the serious sense. It has to know how to bind arguments correctly, how to interpret tool errors, and how to decide whether the tool should have been called in the first place. Gorilla helps explain why typed interfaces are so often the strongest starting point for real agent work.

### [HuggingGPT](https://arxiv.org/abs/2303.17580) (2023)

HuggingGPT is valuable because it widens the meaning of action without collapsing it into unstructured orchestration. Its core contribution is to treat the language model as a controller over specialized capabilities. That is an important step because many real systems do not need a model that can do everything. They need a controller that can decide which specialized system should do what, in which order, with which inputs, and under which constraints (Shen et al.).

The caution is that controller patterns are easy to romanticize. If the specialist tools are poorly typed, if the handoffs are conversational rather than structured, or if the authority boundaries remain vague, the controller simply becomes a more elaborate place for ambiguity to hide. HuggingGPT therefore matters most when read alongside the blueprint's insistence on typed surfaces, normalized observations, and bounded permissions.

### [Mind2Web](https://arxiv.org/abs/2306.06070) (2023)

Mind2Web matters because it forces web action to be treated as a general environment problem rather than as a sequence of handcrafted demos. That move matters for a practical reason. A browser agent can look impressive on a narrow flow and still be brittle in the presence of layout changes, alternative paths, or slightly different page state. By broadening the evaluation frame, Mind2Web helps explain why browser action should be treated as an escalation layer with real robustness costs rather than as the glamorous default for agent systems (Deng et al.).

Its value is partly negative. It makes clear how much work is required before browser action becomes dependable enough to substitute for APIs or structured interfaces. That is useful because it makes the fallback status of browser automation easier to defend. The point is not that browser agents are unimportant. The point is that they should not be chosen when the environment already offers a stronger action surface.

### [SWE-agent](https://arxiv.org/abs/2405.15793) (2024)

SWE-agent is one of the clearest demonstrations of what a strong action interface looks like in a practical domain. The reason it matters is not only that it performs well on software tasks. It matters because the domain itself supplies some of the properties good action systems need: explicit files, executable commands, tests, logs, and machine-checkable outcomes. In other words, the software environment gives the agent an action space with unusually strong replayability and observability. That is why the paper is so instructive even outside software engineering (Yang et al.).

The deeper lesson is that many teams should seek software-like interfaces for non-software work whenever possible. Structured actions, typed artifacts, and testable outcomes are not luxuries reserved for coding agents. They are the things that make action auditable. SWE-agent matters because it shows how much easier agent design becomes when the environment itself supports those properties.

### [BIRD: A Big Bench for Large-Scale Database Grounded Text-to-SQL](https://arxiv.org/abs/2305.03111) (2023) and [Spider 2.0: Evaluating Language Models on Real-World Enterprise Text-to-SQL Workflows](https://arxiv.org/abs/2411.07763) (2025)

BIRD and Spider 2.0 matter because they bring the action discussion back down to an enterprise reality that public agent writing often neglects. A large share of practical agent work is not about general computer use. It is about structured access to data, queries over schemas, and workflows that should be validated against actual records rather than against a visual page. These papers matter because they locate agency inside one of the most commercially relevant action surfaces available today: database interaction (Li et al.; Lei et al.).

They also provide a sobering limit on hype. Text-to-SQL and enterprise workflow action remain difficult even when the surface is more structured than the open web. That should make builders more conservative, not less. If a relatively formal action space still produces hard failure modes around schema drift, multi-step workflow context, and real task complexity, then the case for choosing the strongest available action representation becomes even stronger.
